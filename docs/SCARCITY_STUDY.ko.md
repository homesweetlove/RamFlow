# RamFlow 저메모리 실제 시간 검증 — 2026-11-09

> 이 문서는 배경 제어 개편 전 빌드의 기록입니다. 이후 명시적 배경 우선순위 제어·큐·경량 트레이를 추가한 [별도 후속 실험](BACKGROUND_CONTROL_STUDY.ko.md)과 측정 조건을 구분하세요. 아래 원래 결과는 변경하지 않았습니다.

**이번 검사만으로 “RAM이 부족해도 속도를 유지한다”는 제품 효과를 입증할 수 없습니다.** 기능의 실제 동작과 전경 작업의 성능 이득을 구분합니다. 조건당 두 번의 단일 PC 합성 작업이며, 같은 앱 묶음에 프로그램을 추가한 순이득을 측정한 설계도 아닙니다.

## 완료 시간

실제 전경 Win32 창에서 512 MiB를 할당·의사 난수로 채우고 전체 SHA-256을 세 번 계산했습니다. 명령 전송부터 결과 수신까지 측정했습니다. CPU 연산도 많이 포함하는 합성 작업이며 여유 RAM 행은 블록별 참고값입니다.

| 조건 | 1회 (ms) | 2회 (ms) | 중앙값 (ms) | 실제 정리 합계 |
| --- | ---: | ---: | ---: | ---: |
| 여유 RAM 참고 | 1830.57 | 1791.95 | 1811.26 | 0 |
| 저메모리 · 미실행 | 1895.74 | 1896.36 | 1896.05 | 0 |
| 저메모리 · 관찰만 | 1831.21 | 1875.00 | 1853.10 | 0 |
| 저메모리 · 실제 관리 | 1898.10 | 1857.20 | 1877.65 | 1 |

실제 관리의 중앙값은 미실행 대비 -18.40ms (-0.97%)입니다. 양수는 더 오래 걸렸다는 뜻입니다. 이 차이를 통계적으로 유의한 이득이나 회귀로 부르지 않습니다. 모든 반복과 조건별 메모리 수치를 [CSV](evidence/2026-11-09-scarcity/trials.csv), [프로토콜·결과 JSON](evidence/2026-11-09-scarcity/summary.json)에 보존했습니다.

블록 1에서는 작업 전 정리가 1회 발생했지만 미실행보다 0.12% 오래 걸렸습니다. 블록 2에서는 정리가 발생하지 않았고 미실행보다 2.06% 짧았습니다. 관측된 중앙값의 약 1% 차이를 정리 정책의 효과로 귀속할 수 없습니다.

## 조치 전 조건과 실행 범위

| 블록 | 미실행 가용 RAM (MiB) | 관찰만 (MiB) | 실제 관리 (MiB) | 실제 관리 vs 미실행 시간 변화 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 542.4 | 562.5 | 583.6 | +0.12% |
| 2 | 838.0 | 655.5 | 619.7 | -2.06% |

수치는 개입을 켜기 직전입니다. 외부 부하를 조절해 비슷한 압박을 만들려 했지만 도달한 값은 같지 않습니다. 할당량은 판단 구간 전에 고정했고, 같은 주기의 페이지 읽기는 계속했습니다. 작업 직전 가용 RAM은 별도의 결과이며 CSV에 포함되어 있습니다.

- 비활성 상태를 실제 200초 관측한 뒤 부하를 준비하고 40초 판단 구간을 두었습니다. 센서, Windows API, 전경 확인, 정책과 IPC가 실제 동작했으며 본 비교의 시계는 가속하지 않았습니다.
- 비교 순서는 블록 1 실제 관리→미실행→관찰만, 블록 2 미실행→관찰만→실제 관리입니다. 난수 시드는 20261110입니다.
- 원본 WPF App 어셈블리를 STA 테스트 호스트에서 실행하고 별도 통신 영역의 실제 엔진에 연결했습니다. 배포 프로그램의 일반 시작/SCM 서비스 경로와 모든 사용자 앱에 대한 정책 실행을 재현한 것은 아닙니다.
- 측정 Core는 v0.3.4에 가용 RAM 1 GiB 보호 수정을 적용한 로컬 빌드입니다. SHA-256: `205163c897d364c03610a1c1814c627bdbac3ac5025587fb66e46506fce48996`. 공개 배포 ZIP의 결과로 바꾸어 부르지 않습니다.
- 변경 대상은 2 GiB를 보유한 자체 배경 테스트 PID와 생성 신원으로 제한했습니다. 전경 창 PID와 전체화면 여부도 실제 Windows API로 확인했습니다.
- 8개 작업의 결과 해시가 같았고 대상 밖 변경 요청은 0회였습니다. 안전 부하 해제는 총 0회였습니다. 안전 해제나 무조치 결과가 생겨도 원본에서 제거하지 않는 프로토콜입니다.
- 30분 비활성 뒤의 Memory/CPU Priority·EcoQoS 경로는 이 비교의 시간이 충족하지 않습니다. 본 기록의 성능 판단은 Working Set 축소 경로와 관찰 비용에 한정합니다.

## 프로그램 자체 비용

압박을 만들기 전 비활성 구간의 프로세스별 상주량 중앙값은 UI 약 156.0MiB, 엔진 약 62.7MiB였습니다. 전용 Commit은 각각 약 65.3MiB와 28.6MiB였습니다. 공유 DLL 등의 페이지가 있으므로 두 상주량을 단순 합쳐 시스템의 추가 물리 RAM 사용량으로 부르지 않습니다.

조건별 외부 부하 할당량이 달라 프로그램 자체의 메모리 비용 일부를 압박 맞추기 과정에서 상쇄했습니다. 따라서 특히 미실행 대비 수치를 같은 작업 환경에서의 순성능 이득으로 일반화할 수 없습니다.

## 발견한 문제와 이미 반영한 수정

앞선 가용 RAM 약 2.5 GiB 비교에서는 배경 앱 상주량이 중앙값 약 1,055.6MiB 줄었으나 시스템 가용 RAM 변화는 약 +13.3MiB였고, 해당 배경 앱의 재접근은 54.5→240.5ms로 느려졌습니다. 그래서 1 GiB 이상 여유가 남으면 강제 축소를 보류하도록 수정했습니다.

수정 전후 별도 재현에서는 238.36→56.94ms였지만 **비활성 시계만 가속한 회귀 재현**입니다. 불필요한 회수의 비용을 막은 증거이며, 프로그램 미사용 대비 저메모리 성능 향상으로 쓰지 않습니다. Windows API·IPC를 포함한 171개 assertion과 격리 패키지 검증 통과는 [검증 기록](VALIDATION.md)에 별도로 구분했습니다.

[Microsoft Working Set 설명](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)에 따르면 Working Set에서 제거된 페이지는 RAM에 잠시 남을 수 있고, 수정된 페이지를 재사용하려면 backing store 기록이 필요할 수 있습니다. 따라서 상주량 감소와 응답성 개선은 다른 지표입니다.

## 미완료·예비 시도와 남은 한계

UI 호스트/전경 전환 실패, 부하 해제, 초기 압박 이완, Commit 예약 한계로 중단한 시도도 보존했습니다. 초기 1 GiB 전경 작업에서는 안전 부하가 해제된 비교가 있어 유효한 제품 우위로 채택하지 않았습니다. 512 MiB로 줄인 뒤의 완료된 실험과 섞어 평균내지 않습니다. 시계 가속 예비 실험도 위 표에 합치지 않습니다.

전체 시도 상태와 저장된 작업은 로컬 `benchmarks/2026-11-09-scarcity-review/all-runs.json`, `all-trials.csv`에 있고, 원시 샘플·실행 소스·해시·이벤트는 각 실험 디렉터리에 있습니다. 해당 대용량 원본 경로는 Git에서 제외되어 있으며 위의 소형 JSON/CSV만 저장소 문서에 포함했습니다.

이 테스트는 게임 FPS, 키 입력 지연, 실제 IDE·브라우저·LLM 성능 또는 모든 PC에서의 효과를 입증하지 않습니다. 프로세스 page-fault 누적 횟수는 soft/demand-zero fault도 포함하므로 전경 앱의 디스크 hard fault 수로 해석하지 않습니다. 시스템 Pages Input/sec도 개별 전경 앱에 귀속하지 않습니다.

포트폴리오에는 **실측으로 불필요한 회수의 비용을 발견하고 보호 조건을 수정·검증했다**고 쓸 수 있습니다. **메모리 부족 상황에서도 작업 속도를 유지하는 제품 효과를 입증했다**고 쓰기에는 근거가 부족합니다.
