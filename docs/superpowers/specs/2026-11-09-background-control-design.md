# Explicit background control and lightweight residency

User approved implementation of all three proposed changes and another measured run. Continue on the existing `codex/preserve-warm-pages` branch; retain the preceding uncommitted changes and all previous results.

1. Add opt-in background executable paths. Only these targets can bypass activity/name/task-group exclusions for reversible priority control, without the 30-minute idle wait. System, same-name foreground, whitelist, unknown activity, Windows paths and PID identity checks remain mandatory. Ordinary automatic policy and conservative trim exclusions remain unchanged. Explicit targets can yield resources during a fullscreen foreground task. Restore on foreground, pause, Dry Run, configuration removal, pressure relief or exit. Memory priority is a scheduling hint, not freed Commit.
2. Add a bounded queue for explicitly submitted executable + argument-array jobs. No shell parsing. Concurrency default 1 (range 1–16); require available RAM >= reserve (default 1024 MiB) + declared job estimate, and projected Commit <= 85%. Dry Run/pause never start jobs. Cancel affects waiting jobs only. Running jobs continue on engine exit and their original resource settings are restored. Do not impose allocation-failing hard memory limits or claim arbitrary external-app cache eviction. IPC enqueue requires an administrator, matching live-change authorization.
3. On ordinary UI close, hand off to a separate WinForms tray process and exit WPF after tray readiness is confirmed. The same user-session engine remains alive. UI reopen preserves engine settings. Engine cold startup is Dry Run. Explicit Exit restores/stops the engine. Keep the window if handoff fails. Use test IPC namespaces for integration checks; never operate the user's real engine during tests.

Alternatives: stronger working-set eviction was rejected by measured resume costs; automatically deprioritizing every busy app cannot express user importance; a headless tray alone reduces own footprint but does not establish foreground speed. Implement the targeted controller, admission queue and disposable UI together while measuring their distinct effects.

Verification: test-first policy/queue/lifecycle regressions, Windows setters and IPC, existing Storage/observer/Python suites, packaged WPF checks, real UI→tray→UI handoff. Compare prior and new production Core using identical owned foreground/background workloads and fixed per-block load, randomize order, retain every outcome, report foreground p95 plus background throughput. CPU/mixed-load gains must not be relabeled RAM-only gains. No required speedup is presumed.
