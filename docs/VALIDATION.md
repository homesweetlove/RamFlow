## 2026-11-09 — 저메모리 실제 시간 비교

## 2026-11-09 — 물리 RAM 여유가 있을 때 복귀 지연 보호

가용 물리 RAM이 1 GiB 이상이면 Working Set 강제 축소를 보류합니다. 24 GiB PC에서 2.5 GiB가 남은 경우, 정확히 1 GiB가 남은 경계값, 물리 여유가 있는 Commit 위기, 1 GiB 미만의 기존 회수 경로를 회귀 검증했습니다. 수정 전 불필요한 회수로 실패하는 테스트를 확인한 뒤 수정했으며, Windows API·IPC를 포함한 171개 assertion이 통과했습니다.

실제 Windows 엔진 DLL 전후 비교는 조건별 5회 수행했습니다. 비활성 시계만 가속한 재현 실험에서 1 GiB 캐시 라인 재접근 시간 중앙값은 238.36ms에서 56.94ms로 감소했습니다. 가용 RAM 여유 구간에서 강제 회수를 생략한 결과이며, 같은 메모리 회수량을 유지한 성능 향상이나 PC 전체의 속도 향상을 뜻하지 않습니다. UI·분리 엔진·격리 설치/제거 패키지 검증도 통과했습니다.

## 실사용에서 추가 확인할 항목

동일 작업을 대상으로 Dry Run, 실제 실행을 각각 여러 번 측정하세요. 8GB에서 Chrome + IDE + AI, 16GB에서 Docker + IDE + 브라우저, 게임 중 업데이트, 대용량 복사 등은 Mock 회귀가 있지만 모든 조합의 실제 하드웨어 성능을 검증한 것은 아닙니다.

현재 GUI는 일반 권한으로 동작합니다. 접근 실패는 로그에 기록하며 우선순위 조회에 실패하면 변경하지 않습니다. 관리자 Pagefile 적용/레지스트리 변경/실제 사용자 앱 종료는 자동 검증에서 실행하지 않습니다.

성능 개선 비율을 고정적으로 보장하지 않습니다. Available RAM 증가는 앱 응답성 개선과 같은 지표가 아닙니다.

- 0.3.4: 600개 Mock 프로세스 표에서 실현된 행이 60개 이하인지 확인하고, 선택한 페이지의 표만 갱신합니다. 심한/위급한 압박의 조기 정리, 미확인 활동·활성 앱·전체화면·예외·시뮬레이션 보호 및 Working Set 측정값을 회귀 검증합니다.


- 메모리 측정: 이 컴퓨터에서 실제 WPF 시작과 9개 화면 순회를 3회 비교했습니다. 0.3.3 최대 상주량 중앙값 347.6MiB/전용 263.5MiB에서 소프트웨어 렌더링·미사용 계측 지연 초기화·아이콘 디코딩 제한을 반영한 최종 0.3.4에서 165.0MiB/80.6MiB로 줄었습니다. 같은 화면 작업에서 약 53%/69% 감소입니다. 프로세스 자체의 메모리이며 시스템 전체 사용률 감소나 다른 앱 성능 향상을 뜻하지 않습니다.
