# Readback 시계 보강 v2 — 이전 실패와 분리

2026-11-12. v1 최초 Chrome B는 요청 4.5초에 비해 readback ON 시간이 3.759391700초였다. 제어 타이머의 최대 지연은 0.034258900초였지만, ON 명령 뒤 성공 readback까지의 검증·저널·API 경로가 ON 구간을 소모했다. 이를 CPU 우선순위 API만의 비용으로 단정하지 않는다. v1 배치는 첫 실패 뒤 23슬롯을 미실행으로 남겼고, 원본 seal을 수정하지 않는다. 이 자료는 정책의 성능 우열을 입증하지 못한다.

v2 `real-app-budget-v2-readback-clock`은 다음 실행기 수정만 적용한다. EMA·위험 문턱·9/20 예산·공통 API 조합·0.1초 허용치·대응 0.15초 허용치를 바꾸지 않는다.

- ON epoch의 다음 시각은 `tick 종료 + max(0, 사용한 ON credit × 0.5초 − 현재까지 성공 readback ON 시간)`이다. 이미 발생한 복원 지연은 다음 ON credit에서 차감한다. 복원을 지연하거나 저널을 생략하지 않는다.
- OFF epoch는 `max(tick 종료, epoch 시작 + 0.5초)`에 끝난다. 고정 조건은 고정 **순서**이며, 고정 벽시계 주기라고 부르지 않는다. 명령 지연과 실제 배치 시각은 모두 원시 로그에 기록한다.
- 두 조건 모두 Normal/Contention/Recovery의 측정 구간을 각각 12초로 고정한다. 20 epoch의 nominal 작업은 10초이고 남은 2초는 제어 경로 지연을 위한 여유다. 제어 종료 예정이 12초를 넘으면 실패한다. 프로세스 안전 복원은 실패 여부와 무관하게 수행한다. 다음 제어·사후 종료 시각을 기록해 허용치를 독립 재계산한다.
- 실제 ON 시간 4.5초 ±0.1초와 최종 원복을 여전히 요구한다. 마지막 복원 지연이 너무 크거나 보호 조건 때문에 적용되지 않으면 실패로 남긴다. 같은 wall time은 같은 배경 손실을 보장하지 않는다.
- 자원 적용 직전에도 관측 신선도와 ON 허가를 확인한다. 오래된 관측, 취소, 안전 보호는 예산보다 우선한다. dose 불일치는 실패로 기록하되 안전한 Recovery 단계와 처리율 경계를 끝까지 남긴다.
- 종료 확인은 Job 소속만 보지 않고 SYNCHRONIZE process handle의 signaled 상태를 확인한다. 종료된 PID가 잠시 보이는 것을 실행 중이라고 오인하지 않는다. 알 수 없는 wait 결과는 성공으로 숨기지 않는다.

먼저 **앱별 B/C 한 세션씩, 총 4슬롯**의 실행기 smoke만 수행한다. 통과해도 단일 대응 블록은 효과 검증이 아니다. 실패 시 자동 재시도하지 않는다. 이 단계의 latency 수치를 논문의 우수성 결과로 사용하지 않는다.

```powershell
python -u scripts/research_budget_batch.py --output work/real-app-budget-v2-smoke-20261112 --seed 20261113 --smoke
```
