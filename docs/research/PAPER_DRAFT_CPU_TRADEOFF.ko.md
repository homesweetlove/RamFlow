# Windows 환경에서 전경 작업 보호를 위한 적응형 자원 제어의 효과와 비용 분석

*An Empirical Analysis of the Benefits and Costs of Adaptive Resource Control for Foreground Tasks on Windows*

작성일 2026-11-12. **정규 연구논문을 위한 검토 초안**이며 투고본이 아니다. 저자·소속·기여·연구비를 임의로 채우지 않았다. 평가 대상은 기존 V1이며, CARP의 실앱 성능을 평가한 원고가 아니다. 참고문헌의 R번호는 [집중 선행연구 검토](PAPER_RELATED_WORK_CPU.ko.md)와 같다.

## 초록

백그라운드 작업의 자원 사용을 낮추면 전경 응답을 보호할 수 있지만, 그 대가인 배경 처리량 손실과 제어의 적용 범위를 함께 평가해야 한다. 본 연구는 Windows 사용자 모드 자원 관리 도구 RAM Flow를 이용하여 무개입, 고정 제어, CPU 압박 기반 적응 제어를 비교한다. 단일 이기종 CPU PC에서 명시적 정상 QoS를 요청하는 합성 배경 부하와 격리된 Chrome·VS Code 생성 작업을 결합하고, 조건 순서를 균형화한 36세션을 계획하였다. 개입 전 정상 기준선을 충족하지 못한 1세션을 실패로 보존하고 35세션의 10,900개 요청을 기록하였다. Chrome 검색의 블록별 p95 평균은 무개입 31.88ms, 고정 32.35ms, 적응 32.32ms였으며, 적응 제어의 배경 처리율은 무개입보다 약 37.6% 낮았다. VS Code의 완전 대응 5블록에서는 고정·적응 제어의 코드 완성 p95가 각각 76.01ms와 109.90ms, 배경 처리율은 1,764.4와 4,919.3단위/초였다. 후속 로그 분석에서 적응 제어의 제한 상태 비율은 경쟁 구간의 약 46–48%였고, CPU 압박 감소에 따른 복원과 재진입이 반복되었다. 이 결과는 평가한 조건에서 적응 제어의 일반적 우수성을 지지하지 않으며, 전경 성능의 측정 경계와 배경 손실을 함께 제시해야 함을 보여 준다.

**주제어:** Windows, 전경 응답, 배경 처리량, 자원 제어, QoS, 실증 평가

## 1. 서론

전경 앱과 백그라운드 작업이 같은 CPU를 사용할 때 백그라운드 실행 특성을 조정하는 것은 전경 성능을 보호하는 수단이다. Windows는 이미 우선순위와 QoS를 제공하며, Task Manager Efficiency mode도 낮은 우선순위와 EcoQoS를 결합한다[R1, R2]. 따라서 이러한 API를 호출하거나 전경을 구별하는 사실만으로 새로운 자원 관리 기법이 성립하지 않는다.

평가에는 두 문제가 남는다. 첫째, 전경 지연 감소가 배경 유효 작업의 감소를 동반할 수 있다. 둘째, 시스템 CPU 사용률로 개입을 결정하더라도 해당 앱의 관측 지연이 개선된다고 보장할 수 없다. 지연 목표와 배경 효율의 절충, 실제 성능 피드백의 중요성은 서버 자원 관리에서도 연구되어 왔다[R3, R5, R6]. 본 연구는 이를 새로운 개념으로 주장하지 않고, Windows의 제한된 제어 API를 사용하는 구체적인 구현의 동작과 한계를 평가한다.

연구 질문은 다음과 같다. (RQ1) 같은 API 조합을 지속 적용하는 고정 제어와 압박에 따라 적용·복원하는 V1은 전경 지연과 배경 처리율에서 어떤 운영점을 만드는가? (RQ2) V1의 전환은 어떤 관측과 판단을 거쳐 발생하는가? (RQ3) 안전·재현성 기록을 갖춘 현재 결과로 어느 범위의 성능 주장을 할 수 있는가? 첫 질문은 고정한 일괄 비교로 다루며, 두 번째 질문의 제한 상태 시간과 드라이버 왕복시간 분석은 실험 후 수행한 탐색적 분석으로 구분한다.

본 원고의 산출물은 같은 조치 수준을 확인한 Windows 비교 기록, 실패를 포함한 세션 단위 재현 자료, 압박 게이트와 조치 전환을 연결한 사례 분석이다. 새 스케줄링 원리, 비용 최적성 또는 기존 정책 대비 일반적 우위는 입증하지 않았다. 이러한 실증 결과가 정규 연구논문의 독창성에 충분한지는 별도 검토가 필요하다.

## 2. 배경과 관련 연구

Windows의 스케줄링 우선순위와 QoS는 서로 다른 제어 수단이다. QoS는 이기종 CPU의 코어 선택과 전력 관리에도 영향을 줄 수 있다[R2]. R1의 전경 보호와 CPU 제어 조합은 본 연구의 직접적인 선행 사례다. 본 연구의 고정 B는 R1의 UI 기능을 그대로 실행한 것이 아니라, V1과 동일한 BelowNormal·EcoQoS·메모리 우선순위 조합을 연구 실행기에서 지속 적용한 조건이다. 정확한 API 값과 메모리 조치가 같다고 가정하여 R1과 성능을 직접 비교하지 않는다.

Heracles는 지연 중요 서비스와 best-effort 작업을 함께 실행하기 위한 피드백 제어를 다룬다[R3]. McClure 등의 연구는 서버의 작은 작업에서 정적 할당이 동적 재할당보다 유리할 수 있음을 보고한다[R4]. Cilantro는 성능 피드백과 학습 불확실성을 자원 할당에 연결한다[R5]. Prequal은 분산 요청 배치에서 CPU 부하 대신 지연과 진행 중 요청을 활용한다[R6]. 국내에서도 Android 대화형 작업의 식별·우선순위 부스트와 부하 분산이 제안되었다[R8]. 이 연구들은 전경/지연 인지, 적응형 제어 및 고정형의 유리한 조건이 이미 연구된 주제임을 보여 준다.

본 연구의 차이는 사용자 모드 Windows API, 명시적 소유 배경 PID, 두 생성 앱 작업, readback으로 확인한 조치·복원 상태를 대상으로 한 실증 범위다. 해당 시스템들을 같은 플랫폼에서 비교 실행한 것은 아니며 플랫폼 차이만으로 우수성이나 독창성을 주장하지 않는다. 2025년 CPU/I/O 간섭 제어 연구[R7]는 발행처 초록의 범위만 확인했으므로 상세 비교 근거로 사용하지 않는다.

## 3. 시스템과 실험 방법

### 3.1 제어 경계와 비교 조건

RAM Flow의 판단, 최종 대상 신원 검증, 조치 적용, 원래 값 기록·복원을 분리했다. 실제 속성 변경은 실행기가 만든 배경 PID와 정확한 생성 FILETIME에 한정하였다. 전경 프로세스 보호, 원복 저널, 사용자 예외와 Dry Run 경로를 유지했다. 이번 실제 조치 조건에서는 Dry Run을 끄고 소유 배경 PID에만 변경을 허용했다. 커널 드라이버, 비공식 후킹, CPU Sets 지정, 강제 Working Set 축소는 사용하지 않았다.

| 조건 | 관리 구성 | 소유 배경 PID의 정책 조치 |
|---|---|---|
| A | 엔진·트레이 미실행 | 무개입 |
| B | 격리 엔진·트레이 실행 | 고정 V1 조합: CPU BelowNormal(`0x4000`), 메모리 우선순위 3, 실행속도 QoS Control/State=`1/1` |
| C | 격리 엔진·트레이 실행 | 기존 V1의 압박 게이트에 따라 B와 동일한 조합 적용·복원 |

모든 조건의 배경 워크로드는 실행속도 정상 QoS(Control/State=`1/0`)를 명시한다. A는 **이 공통 입력 조건에서 엔진이 없는 경우**이며, 워크로드 QoS까지 Windows 기본값인 대조군은 아니다. API 원본값, 공통 초기값, 정책 복원값과 워크로드 최종 원본 복원을 각각 기록하였다. 기본 QoS로 수행한 이전 실패/무개입 자료는 보존하되 이번 반복에 합치지 않았다.

### 3.2 V1의 관측과 전환

CPU 압박 상태를 \(h_t\), 관측 CPU 비율을 \(x_t\)라 하면 평가한 엔진의 CPU 게이트는 다음과 같다.

\[
h_t=\mathbf{1}(x_t\ge80)\;\lor\;\{h_{t-1}\land\mathbf{1}(x_t\ge60)\}.
\]

즉 진입 80%, 유지 하한 60%의 히스테리시스가 이미 있다. V1은 지정·보호·신원 등 다른 조건도 검사한다. 이번 경쟁 구간의 성공한 C 전환은 메모리 압박 수준 Normal에서 발생했으며, CPU 압박 플래그가 켜진 판단에서 조합을 적용하고 꺼진 판단에서 복원했다. 전경 지연·배경 유효 처리율은 기록하지만 V1의 결정 입력으로 사용하지 않는다. 별도 CARP 모듈의 비용·쿨다운 기능을 이 C가 사용한 것처럼 설명하지 않는다.

### 3.3 장비·작업·순서

실험은 i5-13400(10코어, 16논리 CPU), OS 보고 물리 RAM 25,430,679,552 bytes, Windows 빌드 26200의 단일 PC에서 수행했다. Chrome은 `157.0.8103.52`, VS Code는 `1.140.0`이며 묶음 안의 앱 바이너리 해시가 동일하였다. 연구 측정 소스는 clean `6e9b1624ba0e3ada219ec6dbf8f06801acdd7ac3`이다.

Chrome은 20,000개 생성 레코드의 검색·정렬 후 상위 1,000행을 갱신한다. VS Code는 5,000개 생성 TypeScript 레코드 문서에서 편집 후 completion provider 또는 save API를 호출한다. 실제 앱 실행 파일을 쓰지만 일상 사용자의 실제 문서·프로젝트 부하를 재현한 것은 아니다. 결과 개수·순서·완성 항목 및 저장 파일 내용을 검사했다.

배경 부하는 4MiB 버퍼를 가진 별도 계산 프로세스다. 유효 작업 한 단위는 의존적인 xorshift64 연산 1,000,000회 완료이며 seed와 체크섬을 고정했다. 스트리밍 계산 작업이므로 실제 빌드 처리율이나 유한 작업 전체 완료시간으로 해석하지 않는다. 단계는 Normal→Contention→Recovery이고 활성 계산 스레드는 1→14→1이다. 각 단계는 목표 10초 및 최소 12라운드를 사용해 실제 경계 시각·경과 시간을 남긴다. 판단 tick은 약 0.5초 간격이며 요청 수행으로 실제 간격이 늘 수 있다.

6개 블록마다 각 앱의 A/B/C를 새 프로필·새 PID·워밍업·5초 이상 정상 기준선으로 실행했다. 각 앱에서 여섯 조건 순열을 한 번씩 사용하고 앱 순서를 seed로 섞었다. 같은 블록의 조건별 실행을 대응시켰다. 6블록은 순서 균형을 위한 고정 실행 규모이며 사전 검정력 계산에 따른 표본 수는 아니다. 연속 실행의 시간 추세나 carryover를 새 PID만으로 제거했다고 보지 않는다.

### 3.4 측정량과 분석

Chrome의 주 지표는 DOM 클릭 핸들러 진입에서 두 번째 `requestAnimationFrame` 콜백까지다. 핸들러 이전의 입력 전달·대기와 실제 디스플레이 표시 완료를 포함하는 지표가 아니다. VS Code는 확장의 편집 시작에서 해당 API 반환까지다. 이 두 경계를 모두 물리적 입력→화면 표시 응답시간이라고 부르지 않는다.

세션/기능/단계별 p95를 계산하고 대응 블록에 같은 가중치를 준다. 배경 처리율은 단계 경계 사이 유효 완료 단위 증가량/실제 경과 시간이다. 검색과 정렬에 반복 표기되는 같은 배경 처리율을 독립 관측으로 중복 계산하지 않는다. 95% 구간은 10,000회 대응 블록 재표집의 percentile bootstrap이며 요청을 재표집하지 않는다. 소표본·미보정 탐색 구간이므로 다중 비교 유의성, 동등성 또는 공동 신뢰 보장으로 쓰지 않는다. 실용적 지연 허용 범위를 결과를 본 뒤 정하지 않았다.

공통 원시 로그에는 정책·설정·소스·바이너리 해시, 단계 시각, 요청, 배경 진행, 원본/적용/복원 readback, 보호 검증·정리 결과를 기록했다. 독립 관찰기는 엔진+실행기 호스트, 트레이, 앱 드라이버와 자기 자신의 자원 사용을 구분했다. 엔진 단독 CPU 비용이나 복원만의 격리 비용은 측정하지 않았다.

## 4. 결과

### 4.1 실패 보존과 동일 조치 검증

36슬롯 중 35세션이 완료되었다. 첫 `b01/code-C`는 정상 기준선에서 Healthy→Ram 분류로 변하고 안정성·도달 기준을 충족하지 못해 개입 전에 실패했다. 경쟁 처치와 본 측정은 시작하지 않았으며 0건의 응답을 성능 0ms로 대체하지 않았다. 원복·정리 후 후속 슬롯을 진행하고 이 슬롯을 재시도하지 않았다. 따라서 Chrome은 6개, Code의 세 조건 완전 대응은 5개 블록이다.

모든 36건에서 초기 설정 복원·소유 Job 정리와 봉인 무결성을 확인했다. 보호 대상 오개입·readback 불일치·원복 실패는 0건이었다. 이는 지정한 시험 대상 범위에서의 관측이며 모든 외부 프로세스에 대한 무오류 보장이 아니다. B/C의 활성 readback은 표 1의 동일 조합이었다. 완료 세션의 전경 요청 10,900건은 기능 정확성 검사를 통과했다.

| Code 저장 p95 평균(ms) | 5 | 24.10 | 22.30 | 25.57 |
| Code 배경 처리율(단위/초) | 5 | 7684.2 | 1764.4 | 4919.3 |

Chrome 검색에서 C−A의 p95 차이는 +0.44ms[탐색적 95% 구간 −0.14,+1.01]이며, 배경 처리율은 약 37.6% 감소했다. 이 측정 경계에서는 C의 지연 이득을 확인하지 못했다. C−B는 −0.027ms[−0.95,+1.13]와 배경 +3341.8단위/초[3276.7,3410.0]였다. 구간이 0을 포함한다는 사실은 B/C의 지연 동등성을 입증하지 않는다.

Code 코드 완성에서는 C−B 지연이 +33.88ms[28.99,39.38], 배경 처리율이 +3154.9단위/초[3013.4,3277.1]였다. C는 B보다 더 많은 배경 진행을 보존했지만 같은 전경 응답을 달성하지 않았다. C−A는 p95 −9.95ms[−22.14,−0.54]였으나 배경 처리율도 약 36.0% 감소했다. A보다 지연이 낮다는 결과만으로 정책 성공을 판정하지 않는다. 저장 지표와 구간별 전체 결과, 효과 크기 및 실패는 공개 CSV에 보존했다.

### 4.3 압박 게이트와 반복 전환: 사후 분석

봉인 로그를 읽기 전용으로 다시 분석해 판단 입력과 성공한 조치 이벤트를 대조했다. Contention의 C 적용 90회는 모두 CPU 압박 true·메모리 Normal·이전 action 0→7이었다. 복원 83회는 CPU 압박 false·메모리 Normal·action 7→0이었다. Chrome 적용 시 CPU는 85.8–97.1%, 복원 시 35.4–47.8%였다. Code는 각각 87.8–98.2%, 39.6–51.6%였다. 두 값 범위가 80/60 게이트를 반복 통과하는 관측은 코드 경로와 일치한다. 단순히 히스테리시스가 없어서 생긴 동작으로 설명할 수 없다.

| 앱의 C 경쟁 구간 | 적용/복원 횟수 | 제한 readback 상태 시간 비율의 블록 평균 |
|---|---:|---:|
| Chrome, 6블록 | 54 / 49 | 47.84% |
| Code, 5블록 | 36 / 34 | 46.22% |

시간 비율은 성공한 OS readback을 경계로 상태가 유지됐다고 보고 단계 경계에서 잘라 계산한 **벽시계 비율**이다. 실제 CPU 할당률, 연속 코어 체류시간 또는 에너지 절감률이 아니다. 같은 정의에서 B는 100%, A는 0%였다. C의 높은 배경 처리율은 제한 시간이 짧았다는 사실과 양립한다. 이 관측만으로 최적 비용 선택이나 고정 듀티 제어보다 나은 적응 효과를 증명하지 않는다.

Code Recovery 초입에도 적용 3회가 기록됐으며 해당 판단의 CPU는 약 91–93%였다. 활성 작업자 수 전환과 CPU 차분 관측 창이 같은 시각에 맞지 않을 수 있다는 코드상의 설명과 일치하지만, 지연 원인의 기여를 분리한 실험은 하지 않았다. 회복 단계 안 복원은 확인됐다. CPU 우선순위·EcoQoS·메모리 우선순위를 묶어 바꾸었고 전환 자체도 별도로 제거하지 않았으므로, 코드 완성 지연을 전적으로 전환 비용이나 특정 API의 탓으로 귀속하지 않는다.

### 4.4 측정 경계와 관리 비용

원래 기록된 드라이버 왕복시간을 사후 보조 지표로 확인했다. Code의 같은 5블록 B/C 왕복 p95 평균은 87.45/112.34ms이고 C−B 차이는 +24.89ms[20.15,29.99]였다. Chrome 검색 C−A는 +0.42ms[0.15,0.71]였다. 보조 지표에서도 C의 일반적 우위를 뒷받침하지 않았다. 이 시간에는 드라이버/CDP 또는 HTTP 경로와 전경 확인 비용이 섞이며 물리적 입력 지연으로 바꾸어 부르지 않는다. 이 사후 분석을 사전 주 지표의 교체나 독립 재현으로 취급하지 않는다.

Code C의 5완료 블록에서 경쟁 구간의 엔진+실행기 CPU 평균은 전체 논리 CPU 대비 0.588%, 트레이 0.055%, 드라이버 0.118%, 관찰기 0.080%였다. 엔진+실행기의 구간 최대 Private Bytes는 블록 전체 최대 32.36MiB, Working Set은 71.75MiB였다. 상주/계측 비용은 실제 관측에 포함되어 있으며 사후 차감해 성능 이득을 만들지 않았다. 순수 Idle·관측 전용·복원만을 분리한 오버헤드 결론은 제시하지 않는다.

## 5. 논의와 타당성의 한계

첫째, CPU 압박은 앱이 받을 실제 지연 이득과 같지 않다. Chrome에서 관측한 API/프레임 경계의 지연 이득 부재는 무개입의 필요성을 검토할 근거지만, 모든 웹 작업이 OS에 의해 충분히 보호된다거나 사용자가 차이를 느끼지 못한다는 증거는 아니다. 화면 갱신 경계와 핸들러 이전 대기가 분리되지 않았으므로 앱 내부 병목의 구체적 원인은 가설로 남는다.

둘째, C와 B의 차이는 조치 강도 외에도 제한 상태 시간, 평가와 적용/복원 횟수, 실행기 비용을 포함한다. 현재 자료로는 전경 목표를 고정했을 때의 배경 처리율 우위 또는 같은 배경 양보 예산에서의 지연 우위를 말할 수 없다. 고정된 시간 비율로 같은 조합을 적용하는 대조군도 없으므로 반복 전환의 이득을 적응형 판단의 고유 기여라고 쓰지 않는다.

셋째, 단일 PC·합성 배경 부하·생성 문서·짧은 단계의 범위를 벗어나는 일반화가 어렵다. 명시적 정상 QoS 입력은 OS 기본 배경 분류와 다르다. 세션은 독립 재시작했지만 같은 장비의 연속 블록이며, 시작 상태 검사도 시간 추세·캐시·전원/주파수·온도의 모든 차이를 통제하지 않는다. 실패로 인해 Code 비교의 완전 순서 균형도 깨졌다. 소표본 bootstrap은 이러한 문제를 해결하지 않는다.

넷째, 배경 전체 완료시간, 장기 기아, 앱 재활성화 지연, RAM 단독 효과, per-process Hard Fault, 사용자 체감 평가 및 CARP의 실앱 예측 정확도는 측정하지 않았다. 시스템 Pages Input을 프로세스 Hard Fault로 대체하지 않았으며 상주 RAM 감소를 성능 개선으로 해석하지 않는다. 성능 결과는 실패를 포함한 원시 세션과 함께 제시한다.

## 6. 결론

같은 Windows API 조합을 사용해도 무개입·고정·CPU 압박 기반 적응 제어는 서로 다른 전경 지연과 배경 처리율을 보였다. 평가한 Chrome 작업에서는 적응 제어의 관측 지연 이득 없이 배경 손실이 있었고, Code 작업에서는 고정 제어의 더 낮은 지연과 적응 제어의 더 많은 배경 진행이 상충했다. 압박 게이트의 반복 전환과 측정 경계를 함께 공개함으로써 결과를 해석할 수 있지만, 현재 증거로 새 알고리즘의 최적성·일반적 우수성 또는 KCI 게재를 주장할 수는 없다.
