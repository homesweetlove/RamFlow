# CPU 압박 실제 파일럿 — 2026-11-10

실험을 실제로 실행했다. **CARP의 우위는 입증되지 않았다.** 기존 원본은 유지하고 새 경로에 저장했다.

- 8스레드 탐색은 CPU 압박에 미달했다. 12스레드 탐색에서는 CPU 86.7~95.5%, 요청447개, 정상 원복을 확인했다.
- 12스레드, 전경8 MiB·배경32 MiB, 시행당8초, 보정6·검증3 블록 × 후보3개 = 27시행을 완료·원복했다.
- CPU 우선순위 모델의 검증3개 중1개가 특징 지원 범위를 벗어나 전체 후보를 거부했다. 통과 기준을 사후 완화하지 않았다.
- CPU+EcoQoS 조치 후 실제 상태가 healthy로 바뀌어 현 모델의 같은 경합 기준선 짝이 없다. 현재 모델이 이 후보 효과를 추정하지 못하는 한계다.

위 표는 무효 시행을 숨기지 않도록 **모든 기록을 포함한 기술통계**다. 무효 시행을 유효하게 바꾼 것이 아니며 효능 추정치가 아니다. 숫자는 요청 전체를 합친 값이 아닌 세션 블록 요약의 평균이다.

현재 분석기는 사후 압박 상태가 목표와 다른 C를 제외하고, 압박 전환이 있는 일부 D를 무효 처리한다. 그러나 개입이 압박 상태를 바꿀 수 있으므로 사후 상태로 조건을 걸면 정책 비교에 편향이 생길 수 있다. 따라서 생성된 CI·효과 크기·Pareto만으로 C/D/E의 우위를 판단하지 않는다. 다음 실행 전에 개입 전 독립 압박 창으로 적격성을 정하고, 조치 후 상태 전환은 결과로 기록하도록 실행기·학습·분석을 함께 수정해야 한다. 이 자료를 재라벨링해 본실험으로 채택하지 않는다.

추가 프로토콜 이탈: 비교 결과 파일16개가 생성된 시점에 실행기3·스케줄28 회귀 검사를 동시에 실행했다. 마지막 블록의 끝 A/B 시행과 겹쳤을 수 있으며 정확한 겹침 시각은 확보하지 못했다. 마지막 블록 전체는 확증 추론에 사용하지 않는다. 모든 자료와 external-activity.json을 보존했고, 표는 이 자료도 포함한 기술 기록이다. 독립된 세션에서 다시 측정해야 한다. 제어용 상태 확인 작업도 파일럿 동안 수행했다.

E/F는 거부 모델로 인해 실제 제어를 하지 않았다. 현재 결과는 비용 모델의 지원 범위 부족과 프로토콜의 사후 상태 조건 문제를 드러낸 실패·한계 자료다. 실제 사용자 앱 지연, 장시간 starvation, RAM/혼합 압박, 여러 PC와 제품 전체 오버헤드는 이번에 측정하지 않았다.

CPU는 자체 생성한 백그라운드에만 부여했다. 사용자 앱의 우선순위 변경·종료, Working Set 강제 축소, pagefile 변경은 하지 않았다. 모든 시행에서 out-of-scope 요청0·원래 설정 원복을 확인했다.

실험 중 변경한 코드는 Python 실행기의 명시적 고부하 선택·스레드 수 전달뿐이다. 네이티브 DLL은 cd699bd 소스에서 빌드했고, 시행별 소스·dirty 여부·바이너리 해시가 원본에 있다. 본 문서는 확증 본실험의 사전 등록이 아니다.
