## 실행·무결성 증거 보완 (2026-11-12 KST)

고정 소스 `6e9b1624ba0e3ada219ec6dbf8f06801acdd7ac3`, 모든 source manifest Dirty=false. i5-13400/10코어·16논리 CPU, OS 보고 물리 RAM 25,430,679,552 bytes, Windows 빌드 26200에서 실행했다. 명령 한 번이 계획 고정→지속 CPU 검사→36슬롯 순차 실행→안전/무결성 검사→분석/표/그래프를 수행했다. 6블록 수는 여섯 조건 순열의 균형을 위한 실행 규모이며 검정력이나 대표성을 보장하지 않는다. 계획을 실행 중 수정하지 않았고 첫 실패를 대체하지 않았다. Windows 전경 제한 때문에 에이전트가 격리 시험 창 활성화를 도왔으며, 일반 장비의 완전 무인 전경 전환을 보장하지 않는다.

### 실제 완료/실패

36슬롯 중 35완료·1실패, 전경 10,900요청. 첫 `b01/code-C`는 개입 전 Healthy 기준선을 충족하지 못했다(Healthy→Ram 분류, Stable=false, Attained=false, 평균 CPU29.31%, Available24.95%, Commit76.95%, System Pages Input1843.57/s). 엔진/경쟁 처치를 시작하지 않았고 전경 본 측정은 0건이다. 이를 실패로 봉인했으며 후속 재실행으로 대체하지 않았다. 원복·정리가 확인돼 사전 규칙대로 후속 슬롯을 진행했다. Code C 대비의 완전 대응 블록은 b02–b06의 5개이며 Chrome은 6개다. 데이터 결측으로 순서 균형의 완성도도 달라졌음을 유의한다.

모든 36봉인 세션의 로그/요약/인덱스/완료 마커·PID 생성 신원·원복과 두 단계 워크로드 복원을 확인했다. 보호 대상 오개입·readback 불일치·원복 실패는 모두 0회, 소유 Job의 남은 PID는 모두 없었다. B/C 활성 readback은 두 앱에서 CPU0x4000·MemoryPriority3·QoS1/1·CpuSets[]로 일치한다. A의 정책 쓰기는 없고, 모든 조건의 공통 워크로드 QoS 초기화/복원은 별도 쓰기 2회다. batch index 3,143파일의 바이트/해시와 고정 계획 해시를 검증했다. ZIP은 임시 런타임 프로필을 제외하고 이 봉인 파일과 원시 소스/버전/해시를 보관한다. SHA256은 무결성 비교이며 외부 서명/인증된 시각이 아니다.

앱 버전은 묶음 안에서 동일하다: Chrome/157.0.8103.52, VS Code1.140.0. 이전 스모크 Chrome .39와 달라 기존 결과를 이번 반복에 합치지 않는다. Chrome 지표는 핸들러→두 번째 rAF, Code 지표는 completion/save API이며 물리적 입력→화면 표시 지연이 아니다. System Pages Input은 per-process Hard Fault가 아니다.

### 결과 해석과 논문 범위

Chrome search의 C−A p95 차이는 +0.44ms [탐색적95%CI −0.14, +1.01]이고 배경 처리량은 약37.6% 감소했다. 개입이 항상 유익하다는 근거가 없고, 이 조건에서는 미개입이 더 나은 선택일 수 있다. C−B는 p95 −0.027ms [−0.95, +1.13], 배경 +3341.8단위/초 [3276.7,3409.96]다. 지연 동등성이 입증된 것은 아니다.

Code completion의 C−B는 p95 +33.88ms [28.99,39.38], 배경 +3154.9단위/초 [3013.4,3277.1]다. 같은 5대응 블록의 B/C p95 평균은 76.01/109.90ms, 처리율은1764.4/4919.3단위/초다. C는 더 많은 처리량을 보존하지만 전경 지연도 더 크다. C−A p95 −9.95ms [−22.14,−0.54]와 처리량 감소도 함께 보고하며 A 대비 개선만으로 성공 처리하지 않는다. 모든 CI는 적은 완전 대응 블록에 대한 미보정 탐색 결과다. 다중 비교/동등성/공동 신뢰/일반적 성능 우위 결론으로 쓰지 않는다. p-value는 생성하지 않았다.

V1은 Contention 안에서 적용/복원을 반복했다. Chrome C의 적용54회/복원49회, Code C의 적용36회/복원34회가 Contention에 기록됐고 Code Recovery에도 적용3회가 있었다. 회복 구간/종료 복원은 확인했지만 무진동 정책은 아니다. 원시 이벤트를 보존한다. 실험 후 이 동작을 고쳐 이번 수치와 같은 버전인 것처럼 서술하지 않았다.

현재 증거는 ‘RAM Flow가 항상 빠르게 한다’ 또는 ‘V1/CARP가 고정보다 우수하다’는 주장에 맞지 않는다. 전경/배경 절충과 불필요한 개입, 입력 QoS에 따른 적용 범위·정책 안정성 한계를 보여 주는 단일 PC 시스템 평가로 정리할 수 있다. KCI 정규 논문의 독창성과 게재 가능성을 이 결과만으로 확정하지 않는다. 당장 추가 측정/기능 개발을 자동으로 시작하지 않으며, 원고의 주장 범위부터 이 결과에 맞춘다. CARP·RAM 단독/혼합·여러 RAM 장비·실제 빌드 전체 완료시간·유의성/동등성 검증은 이번 묶음에서 수행하지 않았다. 스트리밍 완료 작업 단위를 유한 작업 전체 완료시간으로 역산하지 않는다.

### 검증

로컬 Python131테스트(새 batch6·앱14·입장5·분석25·무결성10·matrix28·관찰기38·adapter5), 과거 봉인 v4를 새 분석기로 재생한 36개 metric 행 일치, ResearchLab/Tray Release 빌드 경고/오류0을 확인했다. 신규 코드는 테스트 미존재 실패 후 구현했고 안전 중단·불완전 대응·중복 실행 차단을 검증했다. 측정 코드의 [Native Windows CI](https://github.com/homesweetlove/RamFlow/actions/runs/43152623552), [제품 CI](https://github.com/homesweetlove/RamFlow/actions/runs/43152623445)가 성공했다. Windows API515/IPC525 누적 assertion, 소유 PID CPU/QoS, 연구 통합/실패·취소 로깅도 통과했다. 기능 검사를 성능 세션 수로 합산하지 않는다.
