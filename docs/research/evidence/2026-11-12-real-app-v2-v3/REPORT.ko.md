# RAM Flow 실제 앱 v2/v3 스모크 보고서

보고서 기준: 2026-11-12, Asia/Seoul. 실제 정책 세션은 2026-11-11 23:19~23:55 KST에 실행했다. 원본 UTC 시각은 변경하지 않았다.

**전체 스모크는 아직 미통과다.** Chrome·VS Code의 A/B/C 작업 자체는 모두 실행했고, 원시값·정리·안전 경로의 증거는 확보했다. 그러나 C가 개입할 지속 CPU 압박을 만들지 못해 B/C의 활성 조치 동등성과 적응 제어의 성능 효과는 검증하지 못했다. 논문 성능 우위·게재 가능성은 판단하지 않는다.

## 실행·보존 현황

| 프로토콜 | 실제 실행 | 결과 |
|---|---|---|
| v2 / 4a5e7a9 | 6슬롯+Chrome B 시작 실패 보충 1회 | A/B 완료 4건, C 무개입 미충족 2건, Chrome B 원래 시작 실패 1건 |
| v3 / a7b9e19 | 새 계획의 6슬롯, 각 1회 | A/B 완료 4건, C 무개입 미충족 2건 |

총 13개 실행 기록, 실제 전경 측정이 있는 세션은 12개이며 전경 작업은 **3,744건**이다. 모든 측정 작업의 결과 정확성을 확인했다. v2와 v3는 작업 단위·코드가 달라 독립 반복으로 합치지 않는다. 동일 세션 내 요청도 독립 실험 블록으로 취급하지 않는다.

v2의 원래 Chrome B는 제가 시험 창 활성화 기한을 놓쳐 측정 0건으로 끝난 시작 실패다. 원본을 유지하고 이유를 보충 계획에 먼저 기록한 뒤 별도 경로에서 B를 1회 실행했다. 원래 슬롯/분석을 성공으로 대체하지 않았다. v3에는 보충·대체 실행이 없다.

실행마다 새 프로필·생성 작업 공간과 소유 Windows Job을 사용했다. Chrome은 생성 대시보드 검색/정렬, VS Code는 생성 TypeScript 문서의 완성/저장 API 작업이다. Chrome 지연은 클릭 핸들러 진입→두 번째 rAF, VS Code는 편집→해당 API 반환이다. 물리적 입력→표시 지연이나 임의 웹사이트/실제 대형 프로젝트의 사용자 체감 성능으로 일반화하지 않는다.

실제 앱 버전은 Chrome 157.0.8103.39, VS Code 1.140.0이다. 프로필/개인 앱은 변경하지 않았다. 원래 11월 9/10일 실험, v1 실패 기록, main/research-kci-baseline도 그대로 보존했다.

## 확인한 안전·기록 경로

- 13개 실행 모두 fd17548 계열 run ID·UTC/단조 시각·완료 마커·인덱스/해시·감사 CSV/JSON 검사를 통과했다. 실패 상태도 그대로 일치한다.
- 측정한 12개 세션 모두 원시 요청/단계 경계/배경 누적 작업과 요약이 일치했다. C의 유일한 의미 검증 미충족은 `app_v1_matched_bundle_not_demonstrated`다. 실패를 성공으로 재분류하지 않았다.
- 보호된 전경 오개입·범위 밖 쓰기와 요청/OS readback 불일치는 모두 **0건**이다. 자원 쓰기는 생성한 배경 PID+정확한 생성 FILETIME에만 허용했다.
- A/C는 원래 설정과 일치함을 확인했고, B는 실제 적용 후 종료 readback과 빈 복원 저널을 확인했다. 모든 측정 세션의 앱 Job 정리는 정상이며 잔류 PID와 강제 Job 종료가 없었다. 종료 후 자체 실행기/배경/트레이 잔류도 확인했다.
- B 실제 활성 readback은 두 앱 모두 CPU BelowNormal `0x4000`, MemoryPriority `3`, EcoQoS Control/State `1/1`, CPU Sets `[]`였다. C는 활성 쓰기가 없어 이번 세션에서 B/C 활성 조치 일치를 실측 입증하지 못했다.
- v3 배경 완료 작업 체크섬은 `bd2eeae7775b742c`이며 모든 단계 경계에서 검증했다. 독립 golden vector 테스트도 통과했다.

## CPU 압박을 확인하지 못한 이유와 보강

v2는 32 MiB SHA256/12스레드로도 C의 CPU 80% 개입 임계값을 만들지 못했다. v3에서 한 작업 단위를 1,000,000회의 xorshift64 단계로 분리하고, 16논리CPU 장비에서 14스레드를 사용했다. 이는 합성 부하 도구 변경이며 신규 자원 관리 알고리즘이 아니다. 서로 다른 두 처리율 단위를 합치지 않는다.

초기 부하 점검은 CPU 93.7%, 96.7%, 81.1%를 짧게 관측해 통과했으나 이후 28~35%로 낮아졌다. v3 실앱 워밍업 이후 C의 경쟁 구간 CPU는 Chrome 최대 **34.68%**, VS Code 최대 **44.31%**에 그쳤다. 메모리 기준선도 Healthy였으므로 V1은 개입하지 않았다. CPU가 낮아진 근본 원인은 아직 특정하지 않았으며 OS 제한/하드웨어 문제라고 단정하지 않는다.

이 점검의 기존 3개 상승 표본 기준은 불충분했다. 파일럿 종료 후 별도의 `cpu-preflight-v2-sustained` 규칙을 추가했다. 정상 워밍업 5초/부하 6초, 유효 표본 ≥6개, 표본의 ≥80%에서 CPU≥80%, 마지막 3개도 CPU≥80%를 요구한다. 새 계획 생성과 슬롯 실행에는 이 결과의 성공/정리·작업 단위·스레드 수·동일 관리 바이너리 해시를 함께 요구한다. 증거가 없거나 변하면 앱을 새로 띄우지 않는다.

기존 부하 점검 원시값에 새 규칙을 **사후 재평가하면 실패**다. 원래 결과/원시값은 변경하지 않았고 사후 검토 파일을 분리했다. 이 보강 뒤 추가 부하/정책 비교를 실행하지 않았다. 이전 v3 데이터에 새 사전등록이 적용됐다고 주장하지 않는다. 현재 남은 과제는 지속 압박이 확인되는 입력/환경과 per-process·per-core·affinity/QoS/대기 상태를 확인하는 것이다. 정책 임계값을 낮추거나 실제 센서를 합성해 성공시키지 않았다.

아래는 **앱·조건당 n=1**의 원시 진단값이다. 구간 이름 Contention은 작업자 수를 늘린 구간이며 실제 지속 CPU 압박 도달을 의미하지 않는다. C는 활성 개입 미충족으로 원래 실행 상태가 failed다. 공식 유효 성능 비교/CI/효과 크기·우수성 주장으로 사용하지 않는다.

엔진은 실행기와 같은 프로세스여서 엔진 단독 비용이 아니다. 트레이·앱 드라이버·독립 관찰기는 별도 PID+생성시각으로 측정했다. 서비스와 A의 엔진/트레이는 미실행이며 0으로 채우지 않았다. Python 부모 실행기와 컴퓨터 사용 도구의 상주 비용은 미계측이다. 정책 결정·감사 쓰기·전체 저널 wall time은 JSON에 별도로 남겼으며 모든 로그 경로의 총 CPU 비용은 아니다. System Pages Input은 시스템 전체이고 프로세스별 Hard Fault는 미계측/null이다.

## 검증·버전

로컬 빌드 경고/오류 0개. 앱 계약13·무결성10·분석25·실행기5, 새 CPU 작업 테스트1(독립 golden vector 2개), 지속 압박/계획 차단 회귀5 통과. 기존 disposable Windows 및 실패·취소·로그 중단·alias 통합 검사도 통과했다. 새 지속 압박 테스트는 과도한 단기 상승을 통과시키던 기존 동작에서 먼저 실패한 뒤 보강 후 통과했다.

측정 소스 a7b9e19의 [Native Windows CI](https://github.com/homesweetlove/RamFlow/actions/runs/43041560788)와 [기존 제품 CI](https://github.com/homesweetlove/RamFlow/actions/runs/43041561276)는 성공했다. Windows API/IPC 525 assertions, 새 CPU 작업/기존 disposable/실패 로그 통합 검사도 실제 실행됐다. 이 CI는 실앱 성능 우위를 검증한 것이 아니다. 이후 지속 압박 증거 차단은 2715b87에 분리했으며 로컬 회귀5와 [추가 Native CI](https://github.com/homesweetlove/RamFlow/actions/runs/43045561114), [제품 CI](https://github.com/homesweetlove/RamFlow/actions/runs/43045561032)까지 통과했다. 두 코드 버전의 CI 모두 실제 disposable/실패 로그 검사를 실행했다.

v2 측정 커밋은 4a5e7a9, v3는 a7b9e19다. 각 프로토콜 안에서 관리 바이너리·Core 해시는 동일하고 Git Dirty=false다. 이후 코드를 바꿨다는 이유로 과거 소스/바이너리 해시를 다시 찍지 않았다. [실행 절차](https://github.com/homesweetlove/RamFlow/blob/research/carp/docs/research/REAL_APP_ABC_SMOKE.ko.md), [Draft PR #4](https://github.com/homesweetlove/RamFlow/pull/4)에 코드와 근거를 보존한다.

현 단계에서 논문에 사용할 수 있는 것은 구현·기록·안전 경로의 검증과 개입하지 않은 조건의 진단이다. **C의 실제 개입/복원·B/C 활성 조치 동등성·고정 정책/V1/CARP의 성능 우위는 아직 미검증**이다. 본실험 반복 수와 통계 계획도 이 스모크만으로 정하지 않는다.

증거 ZIP도 짧은 경로에 다시 풀어 13개 실행의 CRC·인덱스·해시·완료 상태를 확인했다. 완료 8건/실패 5건을 그대로 유지했다. Windows의 경로 길이 제한 때문에 ZIP은 `C:\Users\user\Documents\Codex\rfv`처럼 짧은 경로에 풀어 검사한다.
