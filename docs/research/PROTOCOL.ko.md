# CARP 비용 인지 Windows 자원 정책 실험 프로토콜

작성·근거 확인일: **2026-11-10**. 상태: **사전 설계 초안, 본 실험 시작 전**. 새 성능 측정·실제 앱 개입·표본수 확정·가중치 확정은 수행하지 않았다. 아래 수식과 조건은 연구 설계 제안이며 구현 완료나 실측 결과를 뜻하지 않는다. 빈 동결 기록을 채우고 구현과 대조하기 전에는 확증 실험으로 실행하지 않는다.

### 현재 구현 상태: `0.4.0-carp.1`

2026-11-10 작업 트리의 `Contracts.cs`·`ResourcePolicy.cs`·`CarpPolicy.cs`·`JsonPolicyObservationSource.cs`·`Engine.cs` 및 `ResearchReplay/Program.cs`를 읽어 다음 경계를 확인했다.

- `Settings.PolicyName`은 `v1`(기본값)/`fixed`/`carp`다. CARP가 기본 제품 정책으로 켜지는 것은 아니다.
- `CarpOptions`의 foreground/background/reaccess/overhead 가중치는 각각 **1인 미보정 기본값**이다. `EntryMargin=0.02`, `StableSamples=3`, 승격 `CooldownSeconds=30`, 관측 age 최대 10초, `MinIndependentBlocks=3`, 후보 `Confidence>=0.8`이 기본값이다. 이는 파일럿으로 타당화한 연구 설정이 아니다.
- stable 3은 서로 다른 관측 시각의 안정화 확인이고, 모델의 독립 블록 3개와 다르다. JSON의 블록 수·confidence는 외부 제공 메타데이터다. 수치 검증을 통과했다고 실제 독립 표본이나 통계적 신뢰도가 검증되는 것은 아니다. 0.8을 80% CI·성공확률로 해석하지 않는다.
- `JsonPolicyObservationSource`는 **Engine 생성자에서만 주입하는 외부 연구 어댑터**다. 실제 앱 비용 모델은 아직 없다. 기본 관측 공급자 없는 CARP는 자원 조치 후보를 선택하지 않는다. 실측 latency가 optional 필드에 있거나 synthetic estimate가 입력됐다는 사실만으로 인과적 비용 모델이 되지 않는다.
- CARP 조치는 CPU·메모리 우선순위와 허용된 EcoQoS 후보에 한정된다. **Working Set 축소·CPU Sets는 CARP에서 사용하지 않는다.** EcoQoS-only는 현재 LowerCpu 동반 조건 때문에 독립 후보가 아니며, 추가 절제를 구현했다고 가정하지 않는다.
- 큐는 CARP 모드에서 CPU 압박·예약 여유 등의 가드로 **새 시작만 보류**한다. 실행 중 작업을 중지하지 않으며 비용 점수로 큐 후보를 최적화하지 않는다. 따라서 후보 무개입과 별도로 큐 시작 보류가 가능하다. 주 성능 비교에서는 큐를 사용하지 않는다.
- `ResearchReplay`는 같은 snapshot 입력에서 정책 결정을 비교하는 **순수 재생 도구**다. Windows 조치를 하지 않는다. 출력의 판단 시간·예상 점수는 실제 제어 후 앱 성능 결과가 아니다.
- 이 작업의 검증 기록은 **네이티브 Windows+IPC 274개 assertion 통과**, CARP 자체 테스트 자식에 대한 실제 setter·원복을 합성 입력으로 확인했다는 것이다. 이 문서 작업에서는 해당 시험을 재실행하지 않았다. **성능 파일럿·실제 앱 비용 보정은 실행되지 않았다.** 기능/실제 setter 검증을 성능 근거로 바꾸지 않는다.

## 1. 목적·가설·범위

목적은 전경 작업을 위해 배경 작업을 무조건 느리게 만드는 대신, **배경 진행 손실·재접근 비용·관리 비용을 제한한 전경/배경 절충**을 평가하는 것이다. RAM 확보량이나 working set 감소를 성공 지표로 두지 않는다. 기존 [저메모리](../SCARCITY_STUDY.ko.md), [배경 제어](../BACKGROUND_CONTROL_STUDY.ko.md), [실제 앱](../REAL_APP_STUDY.ko.md) 기록은 가설·계측 준비에만 사용하고 새 확증 표본과 합치지 않는다.

연구 질문은 다음과 같다.

1. 혼합 압박에서 E가 A보다 전경 작업 손실을 줄이면서 배경 손실 허용 한계를 지키는가?
2. E가 C·D 수준의 전경 응답을 유지하며 배경 진행량을 더 보존하는가?
3. CPU·RAM 중심 조건과 조치별 절제에서 어떤 작동 범위와 실패가 드러나는가?
4. 정상 상태에서 도구의 상주·관측·판단 비용과 불필요한 개입이 허용 범위 안인가?
5. 전경 전환·관측 소실·부분 적용·복구 실패 때 작업 정확성과 복구 기록이 유지되는가?

신규성·우월성은 가설이다. [관련 연구](RELATED_WORK.ko.md)의 Windows QoS, Acclaim, Heracles를 선행 근거로 인정한다. 커널 reclaim 변경, 자동 종료, 전역 standby purge, pagefile 변경, 서비스 설치, 개인 앱/파일 조작은 본 연구의 조치에 포함하지 않는다.

## 2. 정책과 비교 조건

| 조건 | 동작 정의 | 통제·해석 |
| --- | --- | --- |
| **A — none** | RamFlow UI·트레이·엔진 미실행. Windows 기본 정책은 그대로 동작. | 모든 조건에 공통인 외부 관측기·작업 하네스는 실행한다. A가 계측 없는 PC라는 뜻은 아니다. |

| **F — ablations** | E에서 비용 항목 또는 조치 요소 하나만 바꾼 별도 조건들. | 하나의 F로 합치지 않는다. F1–F5 각각 별도 정책·설정 해시·순서를 갖는다. 보호·신원 확인·감사·복구를 제거하는 절제는 하지 않는다. |

주 비교 B–F의 엔진 호스트·트레이 상태·권한·외부 샘플링·감사 수준·빌드 옵션은 동일하다. UI를 열어 둔 조건과 트레이 조건을 혼합하지 않는다. 과거 V1 바이너리를 별도 실행하는 비교가 필요하면 `D_full` 확장 실험으로 분리한다. 판단 계층 추출에 따른 비용과 제품 전체 배포 경로의 차이를 명시한다.

기본 F 제안은 **F1 배경 비용 점수 제외, F2 재접근 위험 점수 제외, F3 관리 비용 점수 제외, F4 CPU 우선순위만 사용, F5 메모리 우선순위만 사용**이다. F1–F3은 해당 가중치만 0으로 한 별도 설정으로 정의할 수 있다. F4–F5는 외부 후보 목록을 제한하고 그 후보 자체의 보정된 관측이 필요하다. 현재 절제 성능 자료는 없다. 안정화 항목 절제는 사전 목록에 추가한 경우에만 별도 실행한다. F1–F3에서도 해당 비용을 실제로 관측·보고하며, 결측을 0으로 만드는 절제를 하지 않는다. 안전 한계·보호·복구는 유지한다. 예측 위험이 실제 조치 선택에 영향을 주지 않는 구현이면 F2를 수행했다고 주장할 수 없다.

큐의 입장 제어 효과는 별도 Q 실험에서 다룬다. 동일한 유한 배경 작업 목록과 제출 시각을 사용하고, 대기시간·실행시간·전체 완료시간·최대 대기·기아를 측정한다. Q 실험에서만 큐 ON/OFF를 교차하며 주 비교의 효과를 큐에 귀속하지 않는다. 추정 메모리 예약은 실제 할당 상한이 아니다.

## 3. CARP 비용 계약과 동결

개념적으로 후보 조치 `a`에 대한 정규화 예측을 다음과 같이 구분한다.

`S(a) = wL × gL(a) − wB × cB(a) − wR × cR(a) − wO × cO(a)`

- `gL`: 고정한 예측 시간 범위에서 전경 작업 손실/지연 감소 추정.
- `cB`: 배경 진행량 감소 또는 완료 지연 추정. 두 단위를 섞을 때에는 사전 고정한 변환이 필요하다.
- `cR`: 해당 배경 작업을 다시 전경으로 가져올 때의 지연/재접근 위험 추정. 강제 trim을 쓰지 않아도 스케줄링·자연 회수의 비용은 가능하다.
- `cO`: 도구의 CPU·메모리·관측·적용 비용 추정. 실측 자원 지표와 동일한 값이라고 간주하지 않는다.

모든 항목의 단위·분모·정규화 상수·예측 horizon·학습 자료·유효기간·생성 신원·불확실성을 기록한다. 현재 코드는 각 예측을 [0,1]로 검사하고 위 S의 부호를 반전한 **cost 최소화**와 entry margin·최소 단계 승격·안정화를 사용한다. 별도의 배경 손실 hard budget 최적화는 구현돼 있지 않다. 아래 배경 손실 한계는 **실험의 수용/평가 기준**이며 런타임 보장으로 쓰지 않는다. 정확성·신원·최종 전경 재확인 등 엔진 보호를 함께 확인한다. 무개입은 명시적인 후보다. 계약이 바뀌면 본 실험 전에 개정하고 사후에 유리한 수식으로 바꾸지 않는다.

기본 관측 공급자가 비어 있으면 CARP가 무개입하는 구현 계획을 확인했다. 따라서 가짜 효용 관측이나 임의 점수를 공급해 E의 실측 효과라고 부르지 않는다. 실제 앱 지연·배경 진행률과 연결된 비용 모델이 없으면 현재 확인 가능한 것은 기능·무개입 동작이며, 성능 검증 준비 미완료다. 과거 결과의 평균 감소율을 그대로 모든 앱의 `gL`로 넣지 않는다.

## 4. 장치·부하·워크로드 행렬

### 4.1 하드웨어 층

물리 RAM **8 GB, 16 GB, 24 GB 이상** 실물 장치를 각각 포함하는 계획이다. 제품 표기의 GB와 OS가 보고한 usable GiB를 둘 다 기록한다. 가능하면 각 층의 복수 장치와 서로 다른 CPU 구성을 확보한다. 확보하지 못한 층은 미실험으로 남긴다.

RAM 용량과 CPU 세대·코어 수·메모리 채널·속도·SSD·GPU가 다른 PC를 단순 비교해 RAM 용량의 인과효과라고 결론 내리지 않는다. 같은 장치의 RAM 구성 변경은 채널/주파수 차이를 별도 기록한다. 부팅 제한·VM RAM 제한은 실물 8/16 GB 장치의 대체 증거가 아니며 보조 실험으로 분리한다. 장치당 많은 블록이 있어도 독립 하드웨어 수는 늘지 않는다.

Windows edition/build·업데이트, .NET/앱/도구 버전·실행 파일 해시, CPU/P·E 코어·논리 수, RAM, 저장장치 여유·파일시스템, GPU·드라이버, 전원 모드·AC/배터리, 디스플레이 주사율, pagefile/압축 상태, 백신·인덱서 등 실행 환경을 보존한다. 주 실험은 AC로 고정하고 배터리는 별도 층으로 둔다. Windows의 무입력 QoS 변화가 자동화 시험에 미치는 영향도 기록한다. [P1]

### 4.2 자원 조건

| 부하 | 생성 목적 | 파일럿에서 확인할 경계 | 해석 한계 |
| --- | --- | --- | --- |
| **healthy** | 전경 작업+완료 가능한 가벼운 배경 작업, 충분한 여유 | CPU·available·commit·page-in이 동결한 정상 범위에 있는지 | 손실의 분모를 위해 배경 작업은 0이 아닌 유용 작업을 수행한다. 무작업 idle 비용은 별도 보고. |
| **CPU 중심** | 작은 고정 버퍼의 CPU 배경 연산 | sustained CPU 경쟁, RAM/commit 여유·낮은 page-in | 모든 캐시/대역폭 간섭을 제거했다는 뜻은 아님. |
| **RAM 중심** | 페이지가 실제 touch되는 큰 버퍼·긴 주기의 읽기 | available/commit 압박과 paging, CPU 경쟁이 비교적 낮은지 | 단순 reserve 또는 미접촉 allocation을 RAM 압박으로 부르지 않는다. 순수 RAM-only라고 단정하지 않는다. |
| **mixed** | CPU 경쟁과 touch된 메모리 압박을 함께 고정 | CPU·메모리 경쟁이 동시에 유지되는지 | CPU·RAM·EcoQoS 효과를 하나로 RAM 효과라 부르지 않는다. |

기준 환경에서 부하의 프로세스 수·스레드·할당·touch 주기·입력 크기를 파일럿으로 정하고 층/워크로드별로 동결한다. **같은 블록의 조건마다 가용 RAM이나 CPU를 다시 맞추지 않는다.** E의 도구 비용 또는 개입 결과를 외부 부하 조절로 상쇄하면 순효과가 사라진다. 실제 도달한 압박과 시간 경과는 결과로 남긴다. 개입 후 압박이 완화됐다는 이유로 E를 무효화하지 않는다. 파일럿에서 의도한 부하 구분에 실패하면 workload를 수정하고 새 버전으로 기록한다.

### 4.3 합성·실제 작업의 구분

| 묶음 | 전경 | 배경 | 판정 범위 |
| --- | --- | --- | --- |
| S | 해시 등 고정 합성 요청과 독립 정답 | 고정 합성 CPU/RAM 부하, 유용 진행 단위 | 작동 기전·재현성. 사용자 생산성의 직접 증거 아님. |
| H | Chrome 생성 UI 또는 VS Code 생성 문서에서 고정 작업 | 합성 배경 | 실제 앱의 통제 작업. 일반 웹 사용·실제 배경 빌드와 구분. |
| R | 동결한 로컬 프로젝트의 VS Code 편집→TypeScript completion을 주 endpoint 후보로 사용. Chrome 재현 및 다른 작업은 보조 | 소스·입력·명령·정답이 고정된 실제 빌드/압축 등, 진행 마커가 검증된 작업 | 현실성 확장. 개인 코드·계정·사용 중 앱을 사용하지 않는다. |

주 확증 대상은 R의 **한 전경 endpoint와 한 배경 workload**, mixed·healthy의 사전 지정 층이다. VS Code completion 후보를 실제로 계측할 수 없으면 파일럿 단계에서 교체하고 동결한다. 여러 기능 중 결과가 가장 좋은 endpoint를 본 실험 뒤 선택하지 않는다. CPU/RAM/S/H·다른 앱과 F는 기본적으로 기전·탐색 평가이며, 확증 주장으로 승격하려면 표본수와 multiplicity 목록에 미리 넣는다.

Chrome의 자동화 전달→두 번째 rAF는 렌더링 기회 경계 관측이며 실제 디스플레이 표시 완료가 아니다. VS Code API promise 완료는 물리 키 입력→추천 UI 표시·전체 진단 완료가 아니다. foreground HWND→PID만으로 모든 자식/의존 작업을 식별했다고 간주하지 않는다. 전경의 필수 빌드·언어 서버·저장 의존성을 배경 양보 대상으로 지정하면 잘못된 작업 모델이므로 사전 의존성 검증이 필요하다.

## 5. 파일럿 → 동결 → 본 실험

1. **계측 검증:** 무부하 작업 정답·타임스탬프·전경 신원·진행 마커·API 지원·원복을 확인한다. 합성/모의 API 시험과 실제 Windows 시험을 구분한다. 이 문서 작성에서는 실행하지 않았다.
2. **분리 파일럿:** 가능한 하드웨어/부하/작업 층에서 독립 세션 블록을 사용한다. 필요한 파일럿 수와 예산은 시작 전에 기록한다. 지연 분포·블록 간 분산·자기상관·실패·계측 결측·회복 시간·관측기 비용을 파악한다.
3. **모델·가중치 선택:** 파일럿을 학습/검증 세션으로 나누고, 필요한 경우 workload나 장치를 통째로 holdout한다. 요청 단위 무작위 분할로 동일 세션 정보가 양쪽에 새지 않게 한다. 척도와 가중치를 선택한 근거 및 낙관/기준/보수 민감도를 기록한다.
4. **표본 계획:** 실용적 이득·비열등 한계, 실패 허용 기준, 검정력·CI 정밀도 요구를 먼저 정한다. 파일럿의 대응 차이 분산과 장치/일자 구조를 반영해 보수적으로 N을 산정한다. 작은 파일럿의 큰 개선율을 참 효과로 고정하지 않는다.
5. **동결:** 코드·설정·모델·입력·무작위 순서·분석·표본수·최대 시도 수·실패 정책·제출할 주장 목록을 날짜와 해시로 봉인한다. 서명자는 실제 승인한 사람만 기록한다.
6. **새 본 표본:** 파일럿·과거 연구·모델 선택 표본을 재사용하지 않는다. 본 표본을 보고 가중치·timeout·한계·N을 수정하면 해당 자료를 탐색으로 분리하고 새 프로토콜/새 표본이 필요하다.

유의수준 0.05, 목표 검정력 0.90 및 95% CI를 **계획 기본값**으로 제안한다. 실용적 차이와 N은 현재 미확정이다. 초기 근사 `n ≈ ((z(1−α/m)+z(power)) × σd / Δ)^2`는 단일 대응 대비의 출발점일 뿐이다. Δ는 해당 추정 척도에서 귀무 경계와 설계 대립값 사이의 거리다. 주 family 8개와 다중 제약의 **공동 성공 확률**, 불균등 층 가중치·분산·실패율을 반영한 설계 모의분석으로 최종 장치별 블록 수를 정한다. 정밀도 요구 N과 검정력 요구 N 중 큰 값을 선택하고, 파일럿 분산의 보수적 범위에서도 확인한다. 확보 예산이 부족하면 범위·주장을 동결 전에 줄이거나 정밀도 제한 연구로 명시한다. “5회면 충분” 또는 요청 수를 N으로 쓰지 않는다. 모델 입력의 `MinIndependentBlocks=3`은 이 표본 계획을 대체하지 않는다.

## 6. 실험 단위·무작위화·한 블록의 실행

**대응 블록은 동일 장치·부하·workload·입력 seed에서 A–E를 모두 비교하는 하나의 독립 준비 세션**이다. F 비교는 동일 블록에 포함하거나, E를 반드시 포함한 별도 대응 블록으로 사전에 정한다. F를 다른 날의 A와 임의 결합하지 않는다. 각 조건 내부의 요청/센서 샘플은 하위 반복이며 독립 표본이 아니다.

주 확증 설계에서는 장치별 하루 최대 한 독립 블록을 계획한다. 독립성은 새 workload 상태·정책/복구 상태·메모리 부하 준비로 확보하고, 시간적 독립성을 자동 가정하지 않는다. 같은 날 여러 블록을 실행하도록 변경하면 day cluster 구조와 표본 계획을 동결 전에 바꾼다. 다른 장치/날짜·입력 seed에 분산하고, 장치별/층별 arm 위치와 선후행을 균형화한 seeded 무작위 crossover 순서를 사용한다. 홀수 arm 수의 carry-over 균형까지 고려한 Williams형 또는 균형 순서표를 생성·검사한다. 단순 반복 A→B→C→D→E는 사용하지 않는다.

각 블록은 다음 순서를 따른다.

1. manifest·해시·원시 자료 경로·원복 가능 상태를 확인하고 fresh 세션/재부팅 기준을 만족시킨다. 실행 순서 파일을 읽되 결과에 따라 바꾸지 않는다.
2. 각 arm 앞에서 앱·입력·유한 배경 작업·부하를 같은 초기 상태로 준비한다. 조건별 새 PID가 생기므로 경로·해시·생성 시각을 검증한다. 동일 PID 유지가 필수라는 가정을 하지 않는다.
3. 파일럿에서 정한 공통 부하와 warm/cold 절차를 사용한다. warm 실험과 cold 실험을 분리하고 cache purge를 표준 준비 조치로 쓰지 않는다. 이전 arm의 영향이 남으면 전체 arm에 동일한 재부팅 절차를 적용하거나 그 블록을 준비 실패로 기록한다.
4. 외부 관측기와 시계를 준비한다. rate counter의 초기 미성숙 샘플은 결측으로 남긴다. 안정화 길이·워밍업 횟수·측정 길이·요청 간격/도착표는 동결한다. 워밍업은 결과 요약에서 제외하되 원본에 보존한다.
5. 해당 arm의 실제 상태를 확인한다. 이름표만으로 none/dry/V1/CARP를 인정하지 않는다. A의 엔진 미실행, B의 setter 0, C–F의 정책/설정/감사 ID, 실제 적용·무개입 사유와 readback을 기록한다. 관측은 시작·각 작업 배치·종료 및 가능한 변경 이벤트 경계에서 수행한다.
6. 동일 요청 도착표로 전경 작업을 수행하고 모든 요청의 정답/실패를 확인한다. closed-loop 시험만으로 개선 시 요청률도 증가한 상황을 숨기지 않는다. 고정 도착표에서 지연된/건너뛴 요청과 queueing도 기록한다.
7. 전경 측정 창과 동일한 wall-time 창의 배경 진행량을 측정한다. 유한 작업의 완료시간 실험은 별도로 처음부터 끝까지 관측하고, 고정 시간 처리량의 역수를 완료시간으로 대체하지 않는다.
8. 배경 대상의 전경 재전환 probe를 수행해 전환→최초 정상 응답·설정 복구까지를 기록한다. probe 순서·전환 횟수·대기/timeout을 모든 arm에 동일하게 적용한다.
9. 정책 해제 후 원래 우선순위·메모리 우선순위·전력 mask 등 실제 원복을 readback으로 검증한다. 실패하면 저널·이벤트를 보존하고 다음 arm을 시작하지 않는다. working set 바이트를 원래대로 복구했다고 주장하지 않는다.
10. cooldown과 정상 범위 복귀를 확인한 뒤 다음 arm을 준비한다. 최대 대기까지 복귀하지 않으면 중단·잔류 원인·미완료 arm을 기록한다. 숫자가 불리하다는 이유로 재측정하지 않는다.

사람이 arm을 완전히 모르는 것은 어려우므로 자동 정답 검사와 사전 스케줄을 쓴다. 가능한 경우 분석자는 정책명을 가린 ID로 고정 분석을 실행한 뒤 매핑을 연다. 운영자 개입·배경 업데이트·전원/열 변화는 사건으로 기록한다.

| --- | --- | --- |

| 주 task-loss 지표 L | 모든 예정 요청의 `Y = min(정상 정답까지 시간, τ)`의 arm별 p95. 오류/미완료/timeout은 사전 deadline `τ`의 손실값 | 이것은 **deadline으로 상한을 둔 작업 손실**, 성공 latency와 다른 지표다. 실패를 빠른 성공으로 계산하지 않기 위한 사전 정의이며 원시 응답을 덮어쓰지 않는다. τ는 파일럿 뒤 고정. |

| 배경 처리량 T | 고정 전경 측정 창의 검증된 유용 작업 증가량 / 실제 wall seconds | 자식 프로세스·완료 작업도 포함한 작업 집합 경계를 고정한다. no-progress는 측정된 0일 수 있으나 센서 결측은 0이 아니다. |

| 재접근·복구 | 전경 재전환→정상 응답 ms, 설정 복구 readback까지 ms, 실패/재시도/잔류 수 | 정상 완료까지의 비용과 setter 성공·실제 원복을 구분한다. |

| page-in·I/O | `\Memory\Pages Input/sec` pages/s, disk read/write bytes/s·latency·busy 등 지원 지표 | system-wide page input은 전경 PID hard-fault 이벤트 수나 pagefile 전용 읽기가 아니다. |
| 프로세스 메모리 | working set·peak WS·PrivateUsage MiB, PID+생성 신원 | private commit과 resident RAM을 구분한다. 읽힌 일부 PID 합을 도구 전체라고 부르지 않는다. [P2] |
| CPU·관리 비용 | 시스템 CPU%, 프로세스 CPU time/wall time, 정책 계산·샘플링·적용 시간, UI/트레이/엔진별 footprint | `%`의 한 코어 기준/전체 논리 CPU 정규화를 명시한다. 메모리·I/O·시작 비용도 별도 보고한다. [P3] |
| 정책/감사 | eligible/선택/무개입/실제 시도/부분 성공/readback 실패/원복 결과, 점수 성분·모델 ID·관측 age | E가 모든 arm에서 실제 제어됐다고 가정하지 않는다. 의도한 개입과 받은 개입을 구분한다. |

p95는 사전 고정한 동일 quantile 알고리즘(제안: 선형 보간 type 7)으로 arm 안에서 먼저 계산한다. 본 표본은 **블록별 요약**이다. 요청 수가 작은 p95의 불안정성을 파일럿에서 확인하고 요청 수/창 길이를 정한다. 모든 요청을 한데 합친 p95나 p95들의 중앙값을 대응 평균 효과와 바꿔 쓰지 않는다. 이상치는 정해진 workload의 일부이므로 성능이 나쁘다는 이유로 제거하지 않는다.

외부 관측기는 모든 arm에서 동일 버전·우선순위·샘플 주기·출력 정책을 사용한다. 별도 paired calibration에서 endpoint-only/주기 관측 및 내장 계측 OFF/ON의 비용을 평가한다. 자기 측정 CPU·wall cost가 observer의 총 간섭을 포착한다고 가정하지 않으며, 추정 오버헤드를 결과에서 빼지 않는다. 기존 [BENCHMARK](../BENCHMARK.md)의 평균·count만으로 정확한 요청 p95나 시간 커버리지를 복원할 수 없으므로 원시 자료를 추가 수집해야 한다.

## 8. 결측·무효·중단·안전

JSON은 `null`, CSV 수치칸은 빈칸을 사용하고 reason·유효 관측 수·예정 수·유효 시간·최대 gap을 함께 기록한다. 접근 거부·미지원·프로세스 종료·stale·counter 초기화·로그 유실·신원 불일치를 구분한다. `NaN`/무한값을 정상값으로 통과시키지 않는다. PDH rate는 준비된 두 샘플과 status가 필요하다. [P3]

| 사건 | 처리 | 분석에서 보존할 내용 |
| --- | --- | --- |
| 정상 완료가 없는 요청·오답·timeout | 실행 실패로 보존. 주 task-loss 정의에 따라 τ를 부여하고 raw latency와 구분 | 완료율·오답·timeout·손실값, 전체 할당 분모. 성공 요청만의 p95는 조건부 보조 결과 |
| 요청 결과 로그 자체가 없음 | 결과 미확인. 정상 완료/실패나 latency를 만들어 넣지 않음 | 주 endpoint 계산 가능 여부, 최선/최악 경계 민감도. 핵심 결과 미확인 상태에서 우월성 판정 금지 |
| 보조 센서 결측 | 해당 지표만 결측. latency/정답·정책 검증이 온전하면 다른 지표까지 일괄 버리지 않음 | 센서별 coverage·결측 이유. 부분 PID 합·일부 interval 평균을 전체값으로 표시 금지 |
| CARP 필수 관측 결측·오래됨 | 새 개입 차단/필요 복구. E에 할당된 정상 무개입 사례로 남김 | 무개입률·복구·관측 유효성. 실제 적용된 E만 추려 주효과를 계산하지 않음 |
| 권한 부족·API 미지원·부분 적용 | 받은 조치·복구 실패 기록. 완전 적용으로 재표기하지 않음 | 할당 정책 기준 결과와 실제 적용률. per-protocol 분석은 명시적 보조 분석 |
| 잘못된 버전·설정·arm 혼입·작업 초기화 실패 | protocol-invalid 표식, 원본 보존. 사전 정한 재실행 규칙만 적용 | 어느 대비의 paired 값이 없는지 및 원시 실패. 대응을 깨고 독립 표본처럼 대체하지 않음 |
| 자원 안전 한계·작업 오류·복구 실패·감사 실패 | 부하/신규 개입 중단, 허용된 테스트 대상 복구. 다음 arm 보류 | 부하 해제 자체를 성능 성공으로 보지 않음. 발생 arm·시점·한계·미완료 작업 전부 보존 |

주 대비는 A/C/D/E의 필요한 값이 있는 **대응 블록 단위**로 계산한다. 빠진 arm을 다른 블록과 짝짓지 않는다. 완전 대응 성능 분석과 별도로 모든 할당 블록의 실패·미확인·무효 비율을 보고한다. 기술적 실패의 대체 블록은 새 ID/seed를 쓰고 원래 블록을 남긴다. 교체 가능한 사유·최대 대체 수·전체 최대 시도 수를 사전에 고정한다. 제품 유발 실패나 손실이 큰 블록을 “기술적 오류”로 교체하지 않는다. 결측 원인이 정책 의존적일 수 있으므로 complete-case 결론과 보수 경계 분석이 다르면 일반 우위 결론을 내리지 않는다.

전경/시스템/보안/사용자 예외·활동 미확인·PID 재사용 보호는 모든 실제 조치 arm의 공통 경계다. 변경 대상은 명시 테스트 실행 파일·사용자·세션·PID 생성 신원으로 제한한다. 사용자의 실제 앱과 개인 자료는 사용하지 않는다. available/commit·지속시간·온도·전경 timeout·복구 최대시간 등의 중단 한계는 장치별 파일럿에서 정하고 동결한다. 예전 실험 한계를 다른 RAM 장치에 검증 없이 복사하지 않는다. 정책 안정화 시간을 시험 편의로 가속한 결과를 wall-time 성능 표본에 섞지 않는다.

## 9. 추정·CI·효과크기·다중비교

### 9.1 추정 대상

주 분석은 동결한 실물 장치·R workload·입력 분포의 **유한 환경 평균 효과**다. RAM 층을 같은 비중으로, 층 안 장치를 같은 비중으로 가중하는 계획을 제안한다. 장치에서 더 많이 반복했다고 가중치를 키우지 않는다. 장치 수가 적으면 전체 Windows PC 모집단으로 일반화하지 않는다.

블록 `i`, 비교 `X ∈ {A,C,D}`에 대해 `dL_i = log(L_E / L_X)`를 구한다. 평균 log차를 역변환한 비율과 `100×(exp(θL)−1)%`를 보고한다. 음수는 전경 손실 감소다. 같은 블록의 ms 차이도 보고하며 비율들의 중앙값과 평균 log비율을 혼동하지 않는다.

배경 비용은 파일럿에서 장치별로 측정·동결한 양수 기준 처리량 `Tref_h`로 `t=T/Tref_h`를 정규화하고 `dT_i=t_E−t_X`를 쓴다. **0 진행도 유효한 관측**이므로 log(T) 때문에 버리지 않는다. Tref의 원시 단위/수치·출처와 실제 T units/s를 함께 제시한다. 본 실험 A가 양수인 경우의 대응 throughput ratio·손실률도 보조로 보고한다. 0/0이나 결측 분모에는 비율을 만들지 않는다.

주 통계는 장치층별 대응 평균차의 고정 가중합이다. 독립 device-day 블록 가정 아래 `Var(θ)=Σ_h w_h² s_h²/n_h`, Welch–Satterthwaite 자유도의 t 기반 CI·검정을 사용한다. h는 동결한 장치층이다. 소표본·비대칭·이상치 민감도를 위해 **arm 묶음을 통째로 유지한 층화 block bootstrap** CI도 보조 보고한다. 같은 day의 복수 블록을 허용한 설계라면 day 전체를 재표집하는 군집 분석으로 동결해야 한다. 요청/센서 샘플을 bootstrap 독립 단위로 쓰지 않는다. 주 분석을 보고 난 뒤 가장 작은 p값의 방법을 선택하지 않는다.

주 효과크기는 ms 차이·전경 비율·배경 units/s 차이와 정규화 차이다. 보조로 장치별 paired standardized effect `dz=mean(d)/sd(d)` 및 CI를 제시할 수 있으나 원단위 효과를 대체하지 않는다. 분산이 0이거나 N이 부족하면 계산 불가다. 독립 장치/블록 수, 대응 유지 수, 요청 수를 각각 보고한다. 실패율 CI도 블록 군집을 고려하며 요청들을 독립 Bernoulli 표본으로만 계산하지 않는다.

### 9.2 사전 지정 주 family: 8개 단측 검정

한 전경 endpoint·한 실제 배경 workload의 mixed와 healthy에서 다음 8개를 함께 고정한다. δ는 연구자가 정당화하고 파일럿 후 **본 실험 전에** 숫자로 채울 실용적 한계다. δ의 빈칸 상태에서 유의/비열등 판정을 하지 않는다.

| ID | 조건·대비 | 대립가설/판정 방향 |
| --- | --- | --- |
| H1 | mixed E–A 전경 | `θL < log(1−δ_gain)`; δ_gain은 요구하는 최소 개선 비율 |
| H2 | mixed E–A 배경 | `θT > −δ_budget`; 허용 손실 내 보존 |
| H3 | mixed E–C 전경 | `θL < log(1+δ_NI)`; 전경 비열등 |
| H4 | mixed E–C 배경 | `θT > δ_Tgain`; 배경 진행 개선 |
| H5 | mixed E–D 전경 | `θL < log(1+δ_NI)`; 전경 비열등 |
| H6 | mixed E–D 배경 | `θT > δ_Tgain`; 배경 진행 개선 |
| H7 | healthy E–A 전경 | `θL < log(1+δ_healthy)`; 정상 상태 비열등 |
| H8 | healthy E–A 배경 | `θT > −δ_healthyB`; 정상 상태 배경 보존 |

δ_gain은 [0,1), δ_NI·δ_healthy는 양수, 정규화 배경 한계는 비음수로 정한다. 배경 증가의 실용적 최소치 δ_Tgain도 동결한다. 위 대립가설의 반대 영역을 귀무가설로 둔다. “차이가 유의하지 않다”는 비열등·동등의 증거가 아니다.

**Holm 방식으로 family-wise α=0.05를 통제**하고 원 p값·조정 p값·m=8을 모두 보고한다. 미검정/결측 가설이 생겨도 family 수를 줄이지 않는다. 각 주장에는 필요한 gate가 모두 통과해야 한다: 순이득 H1+H2, 고정 대비 절충 H3+H4, V1 대비 절충 H5+H6, 정상 상태 보존 H7+H8. 정확성·실패·복구의 사전 허용 기준도 충족해야 하며 미확인 핵심 결과가 있으면 gate 통과를 확정하지 않는다. [P4]

개별 95% CI는 동시 95% CI가 아니다. 표에는 개별 CI와 함께 8개 대비용 보수적 Bonferroni 동시 한계(단측 신뢰수준 `1−0.05/8`)를 별도 표시해 판정과 구분한다. 추론 범위를 CPU/RAM/여러 endpoint/용량별 개별 주장/F로 넓히려면 **추가 가설 전체와 family 관계·α 배분을 본 실험 전에** 고정한다. 기본 탐색 분석에 조정 p값을 나중에 붙였다고 사전 확증 분석이 되지 않는다.

### 9.3 Pareto·한계·민감도

같은 블록/층에서 `전경 손실↓`, `배경 처리량↑`의 2축 점·대응 선·CI를 제시하고, 재접근·오버헤드·실패 제약을 넘은 점은 표시한다. 점 추정의 비지배 집합을 기술적 Pareto 후보로 보고한다. 불확실성이 겹치면 통계적으로 지배한다고 단정하지 않는다. weighted score가 좋은 정책을 모든 사용자에게 최선이라고 부르지 않는다.

동결한 가중치/손실 예산의 민감도는 별도 탐색 curve로 보여 준다. 본 실험을 보며 가중치를 재조정한 최적점을 E의 확증 결과로 제시하지 않는다. healthy·CPU·RAM·mixed의 불리한 층, 장치별 방향 반전·0 개입·중단·복구 실패를 함께 보고한다. 전체 평균만으로 손실 층을 가리지 않는다.

## 10. 보존·재현·배포 증거

각 **시도**마다 immutable ID, parent block, phase(pilot/confirmatory), 장치·날짜, 할당/실제 arm, order·seed, workload/입력/바이너리/설정/모델/프로토콜 해시, 정책 선택·점수·조치·복구, 요청별 원본·정답, 배경 진행표, 센서 원시값·시각·status, 관측기 비용, 중단·무효·대체 관계를 보존한다. 결과 파일을 덮어쓰지 않고 분석 산출물을 원본과 분리한다. 실패·준비 실패·미완료·안전 해제·무개입을 삭제하지 않는다.

완료된 조건만 있는 CSV는 전체 시도 장부의 대체물이 아니다. 실행 스크립트·버전·환경·분석 코드를 동결한 뒤 원시값에서 표를 재생성할 수 있어야 한다. 공개 경로·라이선스·재배포 권한·원본 hash를 실제로 확인한 뒤 availability 문구를 쓴다. 현재 공개·보관 완료를 가정하지 않는다. 사용자 경로·계정·개인 입력은 공개 산출물에 포함하지 않는다.

[기준선 감사](BASELINE_AUDIT.ko.md)에 따르면 기존 11월 benchmark 디렉터리의 작업별 원본·당시 소스는 현재 및 확인한 이전 사본에서 확보되지 않았다. Git의 요약 CSV/JSON·그림만으로 독립 재현 감사를 완료했다고 쓰지 않는다. 공개 v0.3.4 ZIP의 release digest `e9b86e1f7da3420946e321e6bd64e142f189f414440cc78e19c8cc780bd971df`는 옛 로컬 재포장 ZIP의 실제 hash `d4d2a1c935643b8bf76d58d8330adf5ffbb9e10c3b72988f84c91529de1d443a`와 다르다. 공개 ZIP 자체 재다운로드 검증과 메타데이터 확인도 구분한다. 새 `0.4.0-carp.1`의 기능 시험·재생 결과와 과거 배포/성능 자료를 합치지 않는다.
