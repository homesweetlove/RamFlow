# 현재 증거로 가능한 논문 주장과 투고 준비 상태

2026-11-12 · [검토 초안](PAPER_DRAFT_CPU_TRADEOFF.ko.md) · [선행연구 대조](PAPER_RELATED_WORK_CPU.ko.md) · [36슬롯 원본](evidence/2026-11-12-abc-batch/REPORT.ko.md)

## 판단

**원고 초안 작성과 결과 해석은 가능하다. 지금 자료로 ‘새로운 적응형 알고리즘이 고정보다 우수하다’는 정규 연구논문을 바로 투고하는 것은 권하지 않는다.** 이는 특정 학술지의 판정이나 게재 확률 예측이 아닌, 현재 근거와 주장 사이의 차이에 대한 검토다. KCI라는 이유로 새 지식의 기여가 없어도 된다고 가정하지 않는다.

실험 횟수를 계속 늘리는 것이 당장의 우선 과제는 아니다. 측정·복원·기록의 기반은 갖췄지만, **독창적 기여와 그것을 분리해 검증한 비교**가 가장 약하다. 결과가 불리하다는 사실과 연구 가치가 없다는 판단도 구분한다. 특정 Windows 제어가 언제 비용을 만들고 왜 반복 전환하는지 공개하는 실증 자료로서는 의미가 있다.

## 실제로 확인한 것

| 논문에 쓰려는 주장 | 현재 근거 | 쓸 수 있는 범위 |
|---|---|---|
| 조건 간 실제 API 조치가 같았다. | B/C의 CPU·메모리 우선순위·QoS readback 일치 | 이번 소유 배경 PID/버전에서 확인한 사실 |
| 전경 지연과 배경 진행을 함께 관측했다. | 35완료 세션, 10,900요청, 원시 완료 단위·단계 경계·정확성 확인 | 합성 배경+생성 앱 작업의 측정 경계에 한정 |
| C는 B보다 배경 처리율을 보존했다. | Chrome6/Code5 대응 블록, 각각 약2.85/2.79배의 평균 처리율 | 동시에 Code 지연 악화와 제한 시간 감소를 반드시 보고 |
| C는 같은 전경 응답을 유지하며 처리율을 높였다. | Code 코드 완성 C−B +33.88ms; 실용적 지연 동등 한계 없음 | **현재 입증하지 못함** |
| CPU 압박 게이트의 반복 전환이 있었다. | C의 경쟁 구간 적용90/복원83회 모두 CPU 플래그·action 변화와 일치 | 코드와 로그에 의해 설명되는 동작; 개별 API 효과나 지연 원인의 완전한 인과 분해는 아님 |
| 높은 CPU 압박이면 개입이 유용하다. | Chrome 관측 지연 이득 미확인, 배경 처리율 감소 | **일반화할 수 없음**. 핸들러 이전/화면 표시 지연까지 무효라고 단정하지 않음 |
| RAM 개선, 기아 방지, 실제 빌드 완료시간 개선 또는 CARP 우위 | 이번 묶음에 해당 실험 없음 | 이번 원고에서 성능 결과로 주장하지 않음 |

첫 `b01/code-C`는 정상 기준선 미충족으로 처치 전 실패했으며 재시도하지 않았다. Code의 C 대비는 5개 완전 대응 블록만 사용했다. 실패를 삭제하거나 요청을 독립 반복으로 세어 이를 보완하지 않는다. CI는 탐색적·미보정·소표본이며 동등성/일반적 우위 판정이 아니다.

## 결과가 나온 이유: 확인과 추론 구분

**확인:** V1의 CPU 게이트에는 이미 진입80%·유지60% 히스테리시스가 있다. Contention의 C 적용90회는 CPU 압박=true, 복원83회는 false였다. 메모리 압박은 모두 Normal이었다. 제한 상태 벽시계 비율은 Chrome47.84%, Code46.22%이고 B는100%다. C의 처리량이 크다는 관측을 ‘새 비용 모델이 더 적절한 강도를 골랐다’고 설명하면 잘못이다. 이번 C는 V1이며 조합도 고정되어 있다.

**지지되는 해석:** 같은 14작업자 경쟁 단계에서 적용 후 관측 CPU가 유지 하한 아래로 내려가 복원하고, 이후 다시 진입 임계값을 넘는 전환이 반복됐다. 제어가 바꾼 자원 상태를 개입 필요성 판단에 다시 쓰는 구조와 일치한다. 제한 시간이 짧아 C의 처리율이 A/B 사이에 위치했다는 해석도 자료와 양립한다. 어느 API가 CPU/지연 변화를 얼마나 유발했는지, 반복 전환 자체가 지연 손실의 얼마를 설명하는지는 분리하지 않았다.

**미확인:** Chrome에서 OS가 전경을 완벽히 보호했다거나 렌더링 병목 때문에 차이가 없었다는 설명은 입증하지 않았다. 주 지표가 핸들러→두 번째 rAF여서 입력 전달/대기·실제 표시 완료를 포함하지 않는다는 사실은 코드에서 확인했다. 원래 기록된 드라이버 왕복시간을 사후 분석해도 C의 일반적 우위는 없었지만, 이 역시 물리적 입력 응답이 아니다.

## 선행연구를 대조한 독창성

가장 직접적인 중복은 Windows Efficiency mode다. Microsoft는 이미 낮은 우선순위+EcoQoS로 전경 간섭을 낮추는 방식을 설명했다. Heracles는 지연 목표/배경 효율의 피드백 제어, Cilantro는 실제 성능 피드백·불확실성을 다룬다. NSDI2022의 정책 연구는 고정형이 동적 할당보다 유리한 상황도 보인다. 국내 Android 응답성 인지 연구도 확인했다. [출처·열람 범위](PAPER_RELATED_WORK_CPU.ko.md).

따라서 API 결합, 전경 인지, 적응형이라는 이름, 비용 가중합 수식, 또는 ‘고정형도 이길 수 있다’는 사실만으로 신규성을 구성하기 어렵다. 현재 차이는 **이 Windows 구현·입력 조건에서의 한계와 재현 가능한 관측**이다. 이는 실증 기여의 재료지만, 한 장비·두 생성 작업의 알려진 절충 재확인으로 보일 위험이 있다. 상세 로그와 안전 복원은 자료의 신뢰성을 돕지만 그 자체가 새 과학적 발견을 대신하지 않는다. 문헌 검색이 제한적이므로 최초·유일한 방법이라는 표현도 쓰지 않는다.

## 이번 초안의 위치와 한 가지 남은 핵심 질문

현재 초안은 **제한된 범위의 Windows 시스템 실증 평가**로 작성했다. 효과 없는 조건, 고정형의 더 낮은 지연, 적응형의 반복 전환을 결과로 남긴다. 기존 제품 기능이나 Python 포팅·UI·클라우드·새 AI 기능은 추가할 이유가 없다. RAM Flow 외에 별도 제품을 만들어야 한다는 결론도 아니다.

알고리즘 기여를 중심으로 정규 연구논문을 만들려면 남는 핵심 질문은 하나다.

> **같은 조치와 같은 양보 예산에서, 개입/무개입을 결정하는 규칙이 단순 고정 제어보다 더 나은 전경 지연–배경 진행의 운영점을 만드는가?**

현재 C−B 비교는 제한 시간이 약 절반 대 전체로 달라 이 질문을 분리해 검증하지 못한다. 더 많은 요청이나 같은 실험의 무작정 반복은 이 공백을 메우지 않는다. 향후 이를 진행한다면 비교할 규칙과 응답 목표/배경 예산을 먼저 정해 한정된 검증을 해야 한다. **이번 작업에서는 새 정책 수정·추가 실험을 시작하지 않았다.** 우선 현재 초안과 근거를 인간 저자가 검토해 실증 평가 기여로 원고를 발전시킬지, 위 한 질문을 보강할지 결정할 수 있도록 정리했다.

## 완료/미완료

- 완료: 원시값을 바꾸지 않은 사후 코드·로그 분석, 측정 경계 점검, 국내외 선행 개념 대조, 표와 한계를 포함한 원고 초안, 재현 가능한 읽기 전용 분석기와 구간 계산 검사.
- 미완료: 독립적인 새 알고리즘 기여와 우수성 입증, 최종 투고 원고, 저자 기여/인간 원문 검증과 최신 투고지 형식·AI 사용 공개의 최종 확인. 국내 선행 R8의 게재 서지는 후속 대조로 보완했고, 최종 게재본 본문과 저장소 사본의 동일성은 아직 미확인이다.

R7은 발행처 초록/공식 프로그램 범위만 확인했고 전문은 열람하지 못했다. R8은 저자 연구실 목록에서 39(6), 380–386, Dec. 2012를 확인해 서지를 보완했으나 기관 저장소 사본의 자리표시자/쪽수와 달라 최종 본문의 동일성까지 확인한 것은 아니다. 본 문서의 투고 보류 의견은 게재 불가능 판정이나 학술지의 요구 사항을 대신하지 않는다.
