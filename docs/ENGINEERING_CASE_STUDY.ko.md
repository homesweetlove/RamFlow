# RamFlow — 엔지니어링 사례 연구

> **주제:** 메모리가 제한된 Windows 환경에서 진행 중인 작업을 보호하는 자원 관리  
> **현행 구현:** v0.3.4 · C# / .NET 10 / WPF  
> **검증 결과:** 실제 Chrome·VS Code 재현 작업의 p95 지연 중앙값 45–49% 감소. 앱별 5개 대응 세션·고정 합성 배경 부하·배경 처리량 약 60% 감소를 함께 기록.

[English](ENGINEERING_CASE_STUDY.md) · [README](../README.ko.md) · [최신 아키텍처](NATIVE_ARCHITECTURE.md) · [검증 기록](VALIDATION.md) · [재현 실험 계획](MEASUREMENT_PROTOCOL.md)

## 1. 문제를 어떻게 정의했는가

RAM이 부족할 때 프로세스 종료나 캐시 비우기만 반복하면 일시적으로 사용 가능 메모리 수치가 늘 수 있지만, 중요한 작업이 중단되거나 다시 페이지를 읽어 오는 비용이 생길 수 있습니다.

RamFlow가 다루는 질문은 **“가장 많은 RAM을 확보하는 방법”이 아니라 “사용 중인 작업을 보호하면서 압박 상황에 제한적으로 반응할 수 있는가”**입니다.

설계에 둔 제약:
- 커널 드라이버·문서화되지 않은 후킹·자동 프로세스 종료·Standby List 일괄 비우기 사용 금지
- 활성 창, 동일 이름의 연관 프로세스, 보안·시스템 프로세스, 활발한 CPU/입출력 작업 보호
- 활동 상태·프로세스 신원이 불명확하면 조치하지 않는 보수적 기본값
- 되돌릴 수 있는 설정은 원래 값과 복원 기록을 먼저 저장
- 최적화 도구 자체의 메모리 소비도 측정 대상에 포함

## 2. 판단 흐름

```mermaid
flowchart TD
    A[Windows 자원 계측] --> B[압박 점수 계산]
    B --> C[EMA / 히스테리시스 / 연속 확인]
    C --> D{전체화면 / 일시정지 / 전경 확인 실패?}
    D -->|예| N[관찰만 수행]
    D -->|아니요| E[시스템·활성 작업·사용자 예외 보호]
    E --> F{비활성 대상 확인?}
    F -->|아니요| N
    F -->|30분 이상 비활성 등| G[메모리 우선순위·CPU·EcoQoS 제한 조정]
    F -->|높은 압박 + 짧은 비활성 문턱| H{재검증과 쿨다운 통과?}
    H -->|아니요| N
    H -->|실제 모드| I[프로세스 한 개 Working Set 제한 축소]
    G --> J[원래 값 기록·상태 관찰]
    J --> K{전경/설정 변경?}
    K -->|예| L[원래 값 복원·실패 재시도]
    I --> M[축소 결과 기록]
    N --> A
    L --> A
    M --> A
```

위 도식은 주요 판단 순서를 요약한 것이며 전체 코드 분기를 그대로 복제한 그림은 아닙니다. 구현: [Policy.cs](../native/RamFlow.Core/Policy.cs), [Engine.cs](../native/RamFlow.Core/Engine.cs).

### 압박 판단

사용 가능 RAM, Commit 비율, 페이지 입력, 페이지파일 사용률, Standby 메모리 등을 휴리스틱으로 합쳐 압박을 추정합니다. 압박이 증가할 때 더 빠르게 반영하는 EMA와 연속 확인·히스테리시스를 사용하여 정책이 빈번하게 바뀌는 일을 억제합니다. 극심한 자원 부족에는 별도 위기 조건을 둡니다.

**트레이드오프:** 안정적인 판단을 위해 일부 반응을 늦춥니다. 모든 버벅임을 예측하거나 직접 해결한다고 주장하지 않습니다.

### 작업 보호와 제한적 조치

- CPU·메모리 우선순위/EcoQoS 조정은 **30분 이상 관측된 비활성 상태**와 별도 자원 조건이 있어야 가능합니다.
- Working Set 축소는 **가용 물리 RAM 1 GiB 미만**, **High 이상 압박**, **150MiB 이상 프로세스**, 비활성 **High 10분 / Severe 3분 / Critical 1분** 문턱을 통과해야 합니다. 가용 RAM 여유가 있으면 상주 페이지를 보존해 복귀 비용을 피합니다.
- 축소 시도는 **전체 120초**, **같은 PID 900초** 간격을 지키고, 한 번의 순회에서 최대 한 대상을 시도합니다.
- 조치 직전에 전경·전체화면·대상 신원을 다시 확인합니다. 기본값은 실제 설정을 바꾸지 않는 **Dry Run**입니다.
- 사용 예측 기능은 예정 작업의 보호에 사용하며 선제 축소 근거로 사용하지 않습니다.

**트레이드오프:** 일부 회수 가능한 메모리를 그대로 남기더라도 사용자 작업을 해칠 가능성을 줄입니다.

### 복원과 장애

우선순위 같은 되돌릴 수 있는 설정은 변경 전에 원래 값을 저널에 기록합니다. PID 재사용·프로세스 신원 확인 실패·부분 실패를 구분하고, 복원 실패 기록을 유지하여 재시도합니다. 전경으로 돌아온 앱은 별도의 빠른 확인 경로에서 복원을 요청합니다.

단, **Working Set 축소는 이전 바이트 수로 즉시 되돌릴 수 없습니다.** Windows가 필요 시 페이지를 다시 읽어옵니다. 강제 종료나 전원 손실 직후 즉시 복원할 수도 없으며, 다음 실행에서 저장된 복원 저널을 다시 처리하도록 설계했습니다.

## 3. 시스템 경계

```mermaid
flowchart LR
    UI[WPF UI 및 트레이] <-->|사용자 SID별 Named Pipe| E[사용자 세션의 엔진]
    E --> P[압박 판단 / 보호 정책]
    P --> W[WindowsResourceProvider]
    W --> OS[공식 Windows API]
    E --> J[원래 값 / 복원 저널]
    UI --> S[모델 보관 / 측정 도구]
```

- **프로세스 강제 종료·캐시 삭제** 대신 보호·제한적 조정을 선택했습니다.
- **고정 CPU affinity** 대신 복원 가능한 CPU Sets를 선택했고, 문서화된 API만 사용합니다.
- **WinUI 3 대신 WPF**를 택한 것은 배포 의존성과 구현 환경을 고려한 판단이지 성능 우월성 주장이 아닙니다.
- **클라우드 공간을 RAM으로 사용하는 기능은 없습니다.** 모델 보관은 파일 저장 기능이며 별도 검증·삭제 승인을 요구합니다.

## 4. 실제 앱의 작업 지연을 측정하다

단순 Working Set 축소만으로 전경 성능 이득을 확인하지 못한 [초기 실험](SCARCITY_STUDY.ko.md)을 바탕으로, 사용자가 지정한 배경 작업의 우선순위·EcoQoS 조정, 메모리 여유에 따른 작업 큐, WPF 종료 후 경량 트레이 전환을 구현했습니다. 해결하려는 문제는 **자원 경쟁 중 현재 사용하는 앱의 응답이 늦어지는 것**입니다.

[실제 앱 검증](REAL_APP_STUDY.ko.md)은 단일 PC에서 앱별 5개 새 세션의 미사용/사용을 교차 비교했습니다. Chrome의 생성 대시보드와 VS Code의 생성 TypeScript 문서를 사용했고, 쌍 안에서는 배경 PID와 외부 메모리 할당량을 유지했습니다.

| 재현 작업 | 미사용 | 사용 | p95 지연 감소 |
| --- | ---: | ---: | ---: |
| Chrome 검색 → 렌더링 경계 | 88.15ms | 48.14ms | 45.4% |
| Chrome 정렬 → 렌더링 경계 | 88.56ms | 48.95ms | 44.7% |
| VS Code 편집 → 코드 완성 API | 99.36ms | 50.52ms | 49.2% |
| VS Code 편집 → 저장 API | 62.46ms | 31.60ms | 49.4% |

각 값은 세션별 30회 작업의 p95를 구한 뒤 5개 블록의 중앙값을 계산했습니다. 네 기능 모두 5/5 대응 블록에서 지연이 줄었으며, 배경 처리량은 약 60% 감소했습니다. 20개 조건·1,200개 기능 작업의 결과와 설정 원복을 확인했습니다. **[반복별 CSV](evidence/2026-11-10-real-apps/trials.csv) · [프로토콜·요약 JSON](evidence/2026-11-10-real-apps/summary.json)**

### 앞서 측정한 도구 자체의 비용

저장소의 [검증 문서](VALIDATION.md)는 동일 PC에서 **실제 WPF 실행·9개 화면 순회를 3회 비교**했다고 기록하고 있습니다.

| RamFlow 프로세스 측정값 | v0.3.3 | v0.3.4 | 변화 |
| --- | ---: | ---: | ---: |
| 최대 상주 메모리 중앙값 | 347.6 MiB | 165.0 MiB | 약 **52.5% 감소** |
| 전용 메모리 중앙값 | 263.5 MiB | 80.6 MiB | 약 **69.4% 감소** |

기록된 변경 사항은 소프트웨어 렌더링, 사용하지 않는 계측의 지연 초기화, 아이콘 디코딩 제한입니다.

**주의:** 이는 *RamFlow 프로그램 자체의 메모리* 측정입니다. Windows 전체의 RAM 절약, 다른 앱의 응답 속도 향상, 실제 사용자 생산성 향상을 보여주는 데이터가 아닙니다. 위 0.3.3 → 0.3.4 UI 비교의 개별 반복 원본과 독립 재현 기록은 이 표에 포함되지 않습니다. 이후 수행한 엔진 성능 실험은 별도 기록이며 이 표의 재현으로 합치지 않습니다.

## 5. 근거 자료

[실제 앱 재현 작업의 후속 검증](REAL_APP_STUDY.ko.md)에서는 Chrome의 생성 대시보드 검색·정렬과 VS Code의 생성 TypeScript 문서 코드 완성·저장을 측정했습니다. 동일한 합성 배경 부하에서 앱별5개 대응 블록 모두 개선됐고, p95 중앙값은 Chrome 검색88.15→48.14ms, VS Code 코드 완성99.36→50.52ms였습니다. 배경 처리량 약60% 감소도 함께 공개했습니다. 실제 앱에서 실행한 통제 작업의 결과입니다.

배경 제어 개편 뒤의 [후속 통제 부하 비교](BACKGROUND_CONTROL_STUDY.ko.md)에서는 메모리·CPU 경쟁 부하를 고정한5개 대응 블록에서 전경 요청 p95 중앙값이232.85→131.32ms로43.6% 감소했습니다. 배경 처리량은59.6% 감소했습니다. 사용자 지정 배경 작업이 자원을 양보한 근거로 제시하며, RAM 단독 효과나 전체 생산성 향상으로 일반화하지 않습니다. 작업 큐의 실제 자식 실행과 WPF 종료 후 동일 엔진 유지도 별도 검증했습니다.

후속 [저메모리 실제 시간 비교](SCARCITY_STUDY.ko.md)는 전경 작업의 완료 시간을 직접 측정했습니다. 조건당 2회의 작은 비교에서 미실행 1,896.05ms, 실제 관리 1,877.65ms였지만, 정리가 발생한 반복에서 이득이 없고 초기 압박도 같지 않아 제품의 성능 이득을 입증한 결과로 채택하지 않았습니다. 위 UI 자체 메모리 측정과 구분합니다.

| 주제 | 소스·테스트 | 남은 불확실성 |
| --- | --- | --- |
| 압박 점수와 흔들림 방지 | [Policy.cs](../native/RamFlow.Core/Policy.cs) | 실제 응답성 개선 여부 |
| 보호 대상·조치 빈도 | [Engine.cs](../native/RamFlow.Core/Engine.cs) · [Mock 테스트](../native/RamFlow.Tests/Program.cs) | 모든 외부 앱의 안전성 |
| 원래 설정 복원 | [Engine.cs](../native/RamFlow.Core/Engine.cs) · [검증 기록](VALIDATION.md) | 강제 종료 직후 즉시 복원 |
| IPC 경계 | [EnginePipe.cs](../native/RamFlow.Core/EnginePipe.cs) | 전면적인 보안 감사 |
| UI 자체 메모리 감소 | [검증 기록](VALIDATION.md) | 시스템 전체 RAM·지연시간 개선 |
| 배포 빌드 | [Native CI](../.github/workflows/native.yml) · [로컬 검증](VALIDATION.md) | 외부 하드웨어와 사용자 환경의 재현 |

2026-11-09 로컬 검증에서는 수정 전 실패하는 회귀를 재현한 뒤, 수정 후 Windows API·IPC를 포함한 **171개 assertion**을 통과했습니다. Storage 26개, 외부 관찰기 38개, 기존 Python 회귀 70개 및 격리 패키지 UI·설치/제거 검증도 통과했습니다. 변경 대상은 자체 테스트 PID와 테스트 파일로 제한했으며, 이 통과 기록을 전경 작업의 성능 개선 증거로 대신하지 않습니다.

## 6. 실패 가능성과 추가 검증

| 위험 | 현행 대응 | 추가 검증 과제 |
| --- | --- | --- |
| 스캔 사이 전경 앱 변경 | 조치 직전 재검증·빠른 전경 복원 | 빠른 앱 전환 스트레스 테스트 |
| 활동 정보 부족 | 미확인 대상 보호 | 실제 오탐률 측정 |
| PID 재사용 | 프로세스 생성 신원 확인 | 절전·복귀 시나리오 검증 |
| 조치 일부만 성공 | 원래 값 저널·복원 재시도 | 권한·크래시 조합 실험 |
| Working Set 재접근으로 페이지 입력 증가 | 축소 빈도 제한 | 하드 폴트와 작업 지연 비교 |
| 없는 센서값 | 미지원으로 표시 | 하드웨어 지원 표 |

미실행/실제 개입의 대응 비교와 실제 앱 재현 작업 검증을 완료했습니다. 다음 측정은 CPU 우선순위·메모리 우선순위·EcoQoS의 개별 기여, 빠른 전경 전환, 배경 작업 양보 정도에 초점을 둡니다. Dry Run을 포함한 세 조건 확장 절차는 [재현 실험 계획](MEASUREMENT_PROTOCOL.md)에 보존했습니다.

**핵심 교훈:** 제한된 컴퓨터를 위한 최적화는 무조건 메모리를 많이 비우는 문제가 아니라, 현재 작업을 보호하면서 근거 있는 개입과 복원 정책을 설계하는 문제입니다. 배경 작업의 자원 양보 정책을 구현하고 실제 Chrome·VS Code 재현 작업에서 응답 지연 감소를 측정했습니다. 배경 처리량 감소도 함께 공개해 설계의 효과와 비용을 연결했습니다.
